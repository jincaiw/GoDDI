# Isolated eventlog reference guard fixture

Application builds expose read-only `InspectTx`, `Inspect` and `Verify`, and `Migrate`, which always returns `ErrNoAuthority`. `InspectTx` uses a caller-owned transaction, never begins or ends it, and cannot prevent its caller from ending it or changing connection settings. The caller must enable query_only on a clean connection before beginning that transaction, never write within it, keep the transaction and connection exclusive, exclude other writers and DDL throughout related data reads, and handle all transaction cleanup failures. Inspecting the current PRAGMA cannot establish that the caller did not write earlier in the same transaction; a Version is neither proof of commit nor authorization. `Inspect` identifies `LegacyReference` or `HardenedReference` in one read transaction; `Verify` accepts only the latter. These labels name local candidate database structures, not event-schema, snapshot-schema or RPC versions, and cannot be used for production capability negotiation. The migration runner remains an isolated test fixture, not a production migration. Frozen guard SQL and its digests are shared read-only constants. They accept only an already-initialized exact IPAM 001+002 and `eventlog.Schema` reference. An empty database is rejected; initialization is a separate step using the existing reference initializers. The original SQL and its SHA-256 remain unchanged.

Both inspection versions require positive rowids in the six eventlog and six IPAM tables, correct storage types for the covered authority/head/checkpoint/receipt keys, database integrity and foreign-key checks. This makes legacy inspection stricter than the schema-only `replicaschema.Verify`; acceptance does not establish safe legacy writes, complete data types or authentic history.

`Inspect` and `Verify` require a dedicated caller-owned connection with query_only and foreign_keys enabled, WAL/FULL, busy_timeout=5000, defer_foreign_keys=0 and UTF-8; it does not change these settings. The caller must exclude concurrent connection use, other writers and schema changes. Its single read transaction is an observation of that snapshot, not authorization for other connections or a future state. SQLite source-id equality compares the running driver with its own in-memory reference; it is not a frozen release ID or proof of a specific patch. Cancellation observed through cleanup causes an error retaining the cancellation chain; cancellation after return cannot change the result. If read-transaction rollback reports an error, the verifier attempts to retire the caller-owned physical connection, so it must not be reused. The test performs a real successful rollback and simulates a reported error; it does not establish behavior under a real SQLite rollback I/O failure.

Schema object count, field size and total materialized schema bytes are bounded. Integrity and foreign-key checks and rowid/key scans may visit the whole database; callers must supply isolation, an external database-size/resource limit and an appropriate deadline. This verifier does not guarantee a hard total runtime or memory bound.

Test fault-injection hooks are trusted and must never issue transaction-control SQL; they are not a security boundary. Actual driver COMMIT faults, crashes and power loss have not been validated.

The test-only forward migration installs fixed hidden-rowid collision, positive-rowid and immutable-rowid guards on the six eventlog tables. It also rejects duplicate logical-key INSERTs and logical-key UPDATEs for authority, head and checkpoint. Authority/head cluster keys, checkpoint cluster/source keys, and receipt tenant/scope keys have explicit storage-type guards and historical preflight checks. Existing malformed keys or nonpositive rowids cause rejection, not repair. Remaining non-STRICT fields and business semantics are not fully validated.

Duplicate INSERT guards intentionally reject `INSERT ... ON CONFLICT DO UPDATE`; guarded tables require an independently reviewed same-key UPDATE/CAS and a separate insertion path. Rowid and logical-key guards do not authorize CAS, protect against arbitrary DDL or file access, prove prior history, establish fencing or identify the trusted role. Key reconstruction requires a separately reviewed migration.

`replicaschema.Verify` is now version-aware: it accepts both the legacy and the hardened frozen reference by delegating classification to `InspectTx` and building its comparison reference from `ReferenceDDLs`. `ReferenceDDLs` / `ReferenceMarkerStatements` describe the frozen DDL and marker rows for offline verifiers and isolated fixtures; they are not a migration. **No integration with snapshot installation, application, RPC, production write paths or the same-key UPSERT semantic change is provided here.** Before any future production integration, review version negotiation, compatibility, historical consistency and independent identity/authority evidence.
