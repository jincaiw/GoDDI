# IPAM snapshot row candidate

This eight-table candidate replaces the earlier isolated four-, five- and six-table candidates. These experimental encodings are incompatible even where all are labeled `schema=1`; a production protocol must freeze its schema, negotiate versions and define migration. This document does not claim backward compatibility or a complete snapshot/restore protocol.

NDJSON envelopes are `{"table":"...","row":{...}}` and require snapshotpipeline validation. Every listed column is mandatory even if SQL has a default; nullable columns use explicit JSON `null`. SQL INTEGER values are canonical non-negative decimal **strings**, at most signed 64-bit, with no leading zero except `0`. SQL TEXT values are JSON strings, valid UTF-8 Unicode without unpaired surrogates, no NUL, and at most 4096 UTF-8 bytes. This resource bound and NUL restriction are stricter than the reference SQL TEXT constraints. BLOB values are canonical unpadded base64url: addresses and binary UUIDs are 16 decoded bytes, digests are 32, and receipt response is bounded variable-length GIR1 bytes. A row is at most 2 MiB; the enclosing NDJSON line limit must be separately configured to 2 MiB, and chunks remain at most 1 MiB. Unknown and duplicate columns, generated columns, floats, JSON numeric values and unknown tables are rejected.

Supported tables, in this required order:

- `ipam_tenants`: `id`, `slug`, `display_name`, `revision`.
- `ipam_spaces`: `tenant_id`, `id`, `slug`, `display_name`, `revision`.
- `ipam_prefixes`: `tenant_id`, `space_id`, `id`, `parent_id` (nullable), `family`, `prefix_len`, `first_ip`, `last_ip`, `kind`, `usage`, `site_ref` (nullable), `label`, `revision`. `binary_prefix_bits` is generated and prohibited.
- `ipam_pools`: `tenant_id`, `space_id`, `id`, `subnet_id`, `family`, `pool_kind`, `first_ip`, `last_ip`, `label`, `revision`.
- `ipam_occupancies`: `tenant_id`, `space_id`, `id`, `subnet_id`, `family`, `address`, `kind`, `owner_ref`, `expires_at_ms` (nullable), `created_at_ms`, `revision`.
- `ipam_resource_ids`: `kind`, `tenant_id`, `space_id`, `id`. The five SQL kinds are TENANT (empty tenant/space), SPACE (nonempty tenant, empty space), and PREFIX/POOL/OCCUPANCY (both nonempty); `id` is nonempty TEXT, not necessarily a UUID.
- `static_occupancy_audit`: `cluster_id`, `epoch`, `tenant_id`, `space_id`, `resource_id`, `principal`, `action`, `request_id`, `prior_revision`, `new_revision`, `result`, `occurred_at_ms`, `request_digest`. This restricted candidate accepts only the STATIC-create audit shape (`auditwire`); its primary key is `(tenant_id,space_id,resource_id,new_revision)`, with revision numerically fixed at 1. Cluster is a 16-byte BLOB; digest is 32 bytes.
- `idempotency_receipt`: `tenant_id`, `principal`, `method`, `path`, `idempotency_key`, `request_digest`, `response`, `created_at_unix_ms`, `expires_at_unix_ms`. The primary key is `(tenant_id,principal,method,path,idempotency_key)`: compare decoded 16-byte tenant BLOB as bytes, then TEXT as SQLite BINARY UTF-8. Scope follows the current idempotency API; response is the exact stored GIR1 BLOB validated in place and never reconstructed. It preserves status, ETag and body, not arbitrary HTTP headers. Creation must be positive and expiry later, but no current-time expiry filtering is performed.

Other text keys are nonempty; label and non-null site_ref may be empty. Prefix endpoints, family, masks and kind/usage combinations are checked against the reference DDL. A pool's family is 4 or 6, kind IPAM or DHCP, first <= last, IPv4 has zero high 12 bytes, and an IPv6 closed interval cannot intersect the IPv4-mapped range. Occupancy family, mapped addresses, kind and expiry shape are checked. IPAM TEXT primary key tuples use SQLite BINARY UTF-8 byte order; duplicate or descending keys fail. Audit and receipt keys use their SQL types and orders described above. For the ledger the tuple is `(kind, tenant_id, space_id, id)`.

Rows do not prove referenced scope, subnet containment, pool overlap, DHCP ownership, ledger coverage, authenticity or history completeness. Staging must first import active entities so triggers register their IDs, verify the source ledger includes every generated key, append only missing historical keys, and compare the entire ledger and counts; it must never use REPLACE. Parent/space references, cross-row overlaps, slug uniqueness, lease state, complete auditing/receipt history and other omitted tables require independent validation. Historical audit and receipt rows need not reference still-live resources. SQL-valid rows outside current candidate application constraints are conservatively rejected. The candidate does not authorize or establish readiness to restore or activate a database.

Callbacks may use only caller-controlled disposable staging; errors or incomplete verification require discarding it. Use a fresh Validator for one serial pipeline, and do not call it independently or reenter it while callbacks run. The validator does not open SQLite, authenticate peers or grant a role.
