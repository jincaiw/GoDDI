# GoDDI B8.5 外部验收 Runbook

> 版本：B8.5-0.1（2026-09-12）
>
> 目的：为真实 relay、跨进程事件追平、掉电恢复、双主机网络分区和 Prometheus 监控链路提供可执行的外部验收包。
>
> 重要边界：本 Runbook 是验收准备和证据模板，不代表这些项目已经在本仓完成。只有在指定真实拓扑、真实设备和真实监控系统上执行并保存原始证据后，才能将对应条目标记为通过。

## 1. 验收范围与结论口径

| 编号 | 验收项 | 当前仓内证据 | 外部必需证据 | 当前状态 |
|---|---|---|---|---|
| B8.5-A | 真实 DHCP relay + Option 82 + ACK | Option 82 parser、负向测试、`giaddr` allowlist | 真实 relay、真实客户端、真实 UDP 67/68、抓包 | 未验收 |
| B8.5-B | 跨进程 DHCP→DNS 最终一致性 | `w14h_split_outage_drill.py` 三进程单机写锁演练 | 至少两台主机、独立网络/文件系统、真实 REQUEST/ACK、时间线 | 未验收 |
| B8.5-C | 掉电恢复 | kill -9 / 存储注入 / backup-restore 证据 | 真实电源切断或等价断电设备、持久盘、恢复前后校验 | 未验收 |
| B8.5-D | 双主机网络分区与恢复 | HA 状态机、围栏、takeover/rejoin 代码和进程冒烟 | 两台主机、可控网络分区、真实 fencing/witness、客户端流量 | 未验收 |
| B8.5-E | Prometheus scrape、规则和告警触发 | 指标代码、示例规则、`/metrics` 认证边界 | 真实 Prometheus、`promtool`、Alertmanager/告警接收端、原始时间线 | 未验收 |

**禁止替代：** 单机 SQLite 写锁不能替代跨主机网络分区；环回 UDP 不能替代真实客户端 ACK；示例规则文件存在不能替代 Prometheus 告警实际触发；代码静态存在不能替代真实掉电证据。

## 2. 共同前置条件

### 2.1 软件与版本

每次验收必须记录：

```bash
git rev-parse HEAD
goddi version
uname -a
python3 --version
go version
```

被测二进制必须来自待验收提交，不能混用已发布 `v0.8.0` 与工作树未发布代码。若测试 B8.3/B8.4 工作树改动，先记录构建提交和二进制 SHA256：

```bash
shasum -a 256 ./bin/goddi
```

### 2.2 时间同步与证据目录

所有主机使用 NTP/PTP 同步，验收前记录：

```bash
date -u
# Linux：
timedatectl status || true
# macOS：sntp -sS time.apple.com || true
```

每个验收批次创建独立证据目录，例如：

```text
artifacts/b8.5/<UTC-日期>-<build>-<场景>/
  README.txt
  topology.txt
  commands.log
  events.jsonl
  pcaps/
  metrics/
  logs/
  db-checks/
  screenshots/
```

所有命令、退出码、开始/结束时间和操作者写入 `commands.log`。原始日志和抓包不得只保留截图。

### 2.3 安全与清理

- 测试网络使用专用 VLAN/隔离交换机，不接入生产 DHCP 广播域。
- 测试密钥、管理员密码和 relay 凭据使用临时值，禁止写入仓库。
- 验收结束后撤销临时凭据、删除测试租约和测试 zone。
- 任何会造成广播、租约冲突、磁盘破坏或电源切断的步骤必须由现场负责人确认。

## 3. B8.5-A：真实 DHCP relay / Option 82 / ACK

### 3.1 拓扑

```text
DHCP Client(s) --- client VLAN --- Relay --- relay VLAN --- GoDDI DHCP
                                      |                    |
                                      +-- giaddr           +-- UDP/67
                                      +-- Option 82
```

必须记录：

- 客户端 MAC、厂商、操作系统和 DHCP client 版本；
- relay 厂商、型号、固件版本；
- relay 的 `giaddr`；
- Circuit ID / Remote ID 的原始配置及脱敏值；
- GoDDI 服务端地址、作用域 CIDR、地址池范围；
- 是否启用 ARP 冲突探测及所需权限。

### 3.2 正向步骤

1. 在隔离 VLAN 中创建与 `giaddr` 对应的 DHCP scope。
2. 将 relay 配置为转发 DHCP Discover/Request，并插入 Option 82。
3. 启动抓包：

```bash
sudo tcpdump -i <relay-facing-iface> -s 0 -w artifacts/b8.5/<run>/pcaps/relay-client.pcap 'udp port 67 or udp port 68'
sudo tcpdump -i <server-facing-iface> -s 0 -w artifacts/b8.5/<run>/pcaps/relay-server.pcap 'udp port 67 or udp port 68'
```

4. 启动 GoDDI DHCP 数据面，确认日志显示 scope 和 DHCP server 正常启动。
5. 客户端执行释放/重新获取地址。
6. 保存客户端日志、GoDDI 日志、relay 计数器和抓包。
7. 查询控制面/IPAM/DNS：

```bash
curl -fsS -H "Authorization: Bearer <token>" http://<goddi>:<port>/api/v1/ipam/addresses/view?space_id=<space>&ip=<assigned-ip>
curl -fsS -H "Authorization: Bearer <token>" http://<goddi>:<port>/api/v1/logs/dhcp?page=1\&page_size=100
```

8. 若租约携带 hostname，使用真实 DNS 查询验证 A/PTR 预期行为：

```bash
dig @<goddi-dns-ip> <hostname> A +time=2 +tries=1
```

### 3.3 必须验证的报文事实

从抓包中确认：

- Discover/Request 经过 relay 转发；
- `giaddr` 与配置的 relay allowlist 匹配；
- Option 82 存在且包含预期 Circuit ID / Remote ID；
- GoDDI 返回 ACK，ACK 的地址、租期、server identifier 正确；
- ACK 在真实客户端端口 68 会话上可见；
- 不同 Circuit ID 的客户端落入预期 scope 或策略；
- 未列入 allowlist 的 relay 不获得租约；
- 直接客户端伪造 Option 82 不获得租约；
- 畸形/截断 Option 82 不获得租约，且服务端不崩溃。

### 3.4 通过判据

- 正常 relay 客户端至少连续 20 次 DISCOVER/REQUEST 成功，成功率 100%；
- 至少 3 个不同 Circuit ID、2 个 Remote ID 场景通过；
- 负向场景 100% 无 ACK、无新租约；
- GoDDI 进程无 panic，日志无未预期 ERROR；
- IPAM 关联、DNS 行为与抓包时间线一致。

## 4. B8.5-B：跨进程 DHCP→DNS 最终一致性

### 4.1 拓扑要求

至少两台主机：

```text
Host A：DHCP data plane + local lease store
Host B：DNS data plane + local zone store
Host C：control plane / SQLite（可与 A/B 不同主机）
```

A/B/C 必须使用独立文件系统和独立进程。若共享 SQLite 文件，只能作为开发演练，不得标记 B8.5-B 通过。

### 4.2 步骤

1. 在控制面创建 DHCP scope、DNS zone 和测试租约策略。
2. 启动 Host A/B/C，保存启动日志、`/ready`、控制面 revision 和本地副本摘要。
3. 用真实 relay/client 完成一次 REQUEST/ACK，记录 `T0`。
4. 在 DNS 主机使用 `dig` 循环查询，记录首次返回预期 A 记录的 `T1`：

```bash
for i in $(seq 1 30); do
  date -u +%FT%T.%NZ
  dig @<dns-host> <hostname> A +short +time=1 +tries=1
  sleep 1
done
```

5. 在控制面或跨主机链路制造短时不可达，不修改事实源数据。
6. 在 DHCP 主机再次完成租约变化，记录本地 durable outbox、dirty marker 和事件事实行。
7. 恢复网络，等待上行和 DNS 消费完成。
8. 查询 A/PTR、IPAM 关联、事件事实行和 dirty marker，保存前后快照。

### 4.3 通过判据

- DHCP ACK 已返回后，事件事实最终可在 DNS 数据面消费；
- 事件事实行 append-only 保留；成功上行只清 dirty marker；
- DNS A/PTR 结果与租约 generation 一致；
- 断链期间本地数据面继续按最近有效快照服务；
- 恢复后无重复记录、旧 generation 覆盖新 generation 或脏标记永久残留；
- 每次变化均有跨主机可关联的时间戳、lease ID、generation 和 revision。

## 5. B8.5-C：真实掉电恢复

### 5.1 环境

- 独立测试主机或可控电源插座；
- 持久化 SSD；
- UPS 状态已记录；
- 测试数据库和日志位于被测持久盘；
- 具备远程控制台，避免断电后无法取证。

禁止用 `kill -9` 直接替代掉电结论。`kill -9` 只能作为崩溃一致性补充场景。

### 5.2 步骤

1. 写入一批已知租约、DNS 记录、IPAM 状态、配置 revision 和 durable outbox 事件。
2. 在客户端持续发送可重复的 DHCP renew，在 DNS 端持续查询。
3. 记录断电前数据库文件、WAL 文件、应用日志、指标和最后事务 ID。
4. 在随机时刻切断电源，记录断电时间。
5. 恢复电源并记录启动时间、迁移日志、恢复闸门结果和 `/ready`。
6. 校验数据库完整性：

```bash
sqlite3 <control.db> 'PRAGMA integrity_check;'
sqlite3 <control.db> 'PRAGMA foreign_key_check;'
sqlite3 <lease.db> 'PRAGMA integrity_check;'
sqlite3 <dnsdata.db> 'PRAGMA integrity_check;'
```

7. 对比断电前后：
   - 最后已确认 revision；
   - active lease 和 generation；
   - DNS 记录与删除事件；
   - dirty marker；
   - 审计记录；
   - WAL replay 后的计数和唯一性。

### 5.3 通过判据

- 数据库完整性检查通过；
- 不出现重复租约、重复地址或违反唯一约束的数据；
- 已提交事务不丢失；
- 未提交事务可以回滚，不产生半行或伪造 ACK；
- 服务启动后按自身 migration ceiling 正确接受/拒绝归档；
- `/ready` 只在数据面恢复到可服务状态后变为 `ok`；
- 未确认数据窗口、可能重复事件和恢复重放结果均有明确记录。

## 6. B8.5-D：双主机网络分区与恢复

### 6.1 前置条件

- 两台独立主机 A/B；
- 可控交换机 ACL、Linux bridge、网络仿真器或硬件隔离；
- 明确 fencing/witness 机制；
- 测试客户端可分别固定走 A、B 或通过外部网络层切换；
- 分区注入不应通过停止进程代替。

### 6.2 步骤

1. 记录两节点角色、lease watermark、revision watermark、ready 状态和对端心跳。
2. 正常执行 DHCP renew、DNS 查询和配置读取，保存基线。
3. 只切断 A↔B 的同步/控制链路，保留客户端到各节点的必要业务链路。
4. 验证未授权节点不能继续承诺超出其水位的新租约或配置。
5. 执行明确的 fencing/takeover 操作，保存命令和操作者身份：

```bash
goddi ha status
goddi ha fence <node>
goddi ha takeover <node>
goddi ha rejoin <node>
```

6. 恢复节点间网络，观察 watermark/gap 对账、旧 leader fencing 和 rejoin。
7. 重复一次反向分区，避免只验证单一方向。

### 6.3 通过判据

- 分区期间最多一个节点被授权承诺同一资源；
- 旧 leader 被 fencing 后不能继续写入；
- takeover 前有明确水位/gap 检查和稳定窗口；
- split-brain 负向场景拒绝服务或进入明确 degraded，不 fail-open；
- 恢复后自动或按 runbook 完成对账；
- 不出现双写、租约重复、配置 revision 分叉未报告或数据静默覆盖。

> 当前仓的 `internal/cluster` 多节点协调仍未实现；在该能力未完成前，本项只能作为外部验收设计，不能声称 GoDDI 已通过 B8.5-D。

## 7. B8.5-E：Prometheus / promtool / 告警触发

### 7.1 采集配置

1. 使用真实 Prometheus，不使用仅 `curl /metrics` 的替代证据。
2. 按部署安全要求配置认证；当前 `/metrics` 未认证访问应按产品契约返回 401。
3. 保存 Prometheus 配置、target 状态和版本：

```bash
prometheus --version
promtool check config prometheus.yml
promtool check rules rules/*.yml
```

4. 采集以下基础指标：

```text
goddi_dhcp_requests_inflight
goddi_dhcp_request_queue_depth
goddi_dhcp_request_queue_capacity
goddi_dhcp_requests_dropped_total
goddi_dhcp_request_timeouts_total
goddi_dhcp_sql_busy_total
goddi_dataplane_ready
goddi_dataplane_pending_changes
goddi_db_errors_total
```

### 7.2 触发场景

至少验证：

| 场景 | 注入方式 | 预期指标/告警 |
|---|---|---|
| DHCP 队列压力 | 真实客户端/relay 并发请求 | queue depth 上升，满队列时 dropped 增加 |
| 控制库不可写 | 受控权限/网络故障 | readiness degraded、pending/refused 增加 |
| 上游 DNS 失败 | 隔离上游 | upstream unhealthy、SERVFAIL 或对应告警 |
| 数据库连接/锁压力 | 受控测试数据库场景 | DB error/SQL busy 增加 |
| 节点分区 | 真实网络 ACL | HA/readiness/复制延迟告警 |

### 7.3 通过判据

- `promtool` 检查通过；
- Prometheus target `up=1` 且 scrape 时间线连续；
- 每个故障注入都有指标变化、规则评估结果和告警接收记录；
- 恢复后指标回落、告警 resolved 事件可见；
- 指标标签无客户端 MAC、hostname、原始 Option 82 或高基数 IP；
- 规则不会把从未启用的 HA、备份或 DNSSEC 能力误报为故障。

## 8. 证据归档模板

每个场景至少归档：

```text
README.txt                 # 版本、拓扑、操作者、结论、未通过项
topology.txt              # 主机/IP/VLAN/relay/端口/版本
commands.log               # 每条命令、时间、退出码
logs/                      # GoDDI、relay、客户端、Prometheus、Alertmanager
pcaps/                     # 原始 pcap，不只保留截图
metrics/                   # /metrics 原文、Prometheus query/export、规则评估
 db-checks/                # integrity_check、foreign_key_check、行数/水位快照
screenshots/               # 控制台和告警界面辅助证据
```

结论必须使用以下之一：

- `PASS：证据完整，满足本 Runbook 判据`；
- `PARTIAL：仓内或单机证据成立，但外部前置条件/证据不足`；
- `FAIL：实际行为不满足判据`；
- `BLOCKED：缺少真实拓扑、设备、权限或协调能力，未执行`。

禁止使用“基本通过”“代码已具备因此通过”等无法复核的结论。
