## 二、已修复问题（本次检查中发现并修复）

1. **[严重/性能] 统计与仪表盘查询全表扫描**（`internal/api/handler/stats.go`、`internal/metrics/handler.go`，commit `195a645`）
   - 现象：`/api/v1/stats?range=day` 539s、`/api/v1/dashboard` 636s、后续请求排队 483s；容器 CPU 持续 ~101–106%。
   - 根因：SQL 使用 `WHERE datetime(created_at) >= datetime(?)`，列上的 `datetime()` 包裹使 `idx_dns_query_logs_created_at` 失效，对 4184 万行做全索引扫描并逐行调用 `datetime()`。
   - 修复：SQL 参数改为 SQLite 原生 `YYYY-MM-DD HH:MM:SS` 格式（与 schema 默认值 `datetime('now')` 一致），改为裸比较 `created_at >= ? AND created_at <= ?`，命中索引区间搜索（EXPLAIN：`SEARCH ... USING COVERING INDEX`）。API 响应中的 `Start`/`End` 保持 RFC3339，对外兼容。
   - 新增回归测试：断言 EXPLAIN QUERY PLAN 使用索引（`TestQueryLogRangeQueryUsesIndex`、`TestGetStats_RangeAndIndex`）。
   - 实测（生产库）：小时窗口 <10ms；日窗口 ~45s（4184 万行聚合的固有成本）；修复后容器 CPU 降至 0.04%。

2. **[严重/部署] compose 部署的容器无法绑定 :53/:67，DNS/DHCP 以 degraded 模式启动**（`Dockerfile`、`docker-compose.yml`，commit `195a645`）
   - 现象：按 compose 重建后 `/health` 返回 degraded，日志报 `bind: permission denied`。
   - 根因：镜像以非 root 用户 `goddi` 运行；`cap_add: NET_BIND_SERVICE` 会在非 root exec 时失效；`network_mode: host` 下又不能使用 `net.ipv4.ip_unprivileged_port_start` sysctl。
   - 修复：Dockerfile 中 `setcap cap_net_bind_service=+ep /usr/local/bin/goddi`（文件 capability 对非 root 生效），compose 保留 `cap_add` 维持 bounding set。修复后容器 healthy、DNS/DHCP 正常启动。

3. **[质量/CI] lint 体系修正**（此前批次，commit `b92a1e3` 等）
   - golangci-lint-action 升级 v7 并固定 `version: v2.13.2`（v6 不支持 v2 配置；"latest" 解析到旧 Go 构建的二进制无法处理 go 1.26）。
   - 清理 33 项 lint 告警，其中包含 1 个真实缺陷：metrics 采样 ticker 中 `sampleProviders()` 调用丢失导致缓存/日志丢弃指标永不更新。

4. **[前端] 每页下方一整屏空白**（commit `533e60d`，本会话早前已修复并浏览器验证）
   - `createDiscreteApi` 向 body 传送的空 `.n-config-provider` 命中全局 `min-height:100vh` 规则；选择器限定为 `#app > .n-config-provider`。

## 三、未解决问题（风险声明）

1. **查询日志容量增长风险（WARN）**：当前流量下 `dns_query_logs` 约 11.6 GB/天（41.8M 行/天），保留 30 天意味着数据库可能增长到数百 GB，且日级统计聚合 4184 万行需要 ~45s。建议：上线前评估缩短保留期（如 7 天）、或对高频客户端启用采样/关闭记录、监控磁盘水位（`docs/prometheus-alerts.yml` 已含 DroppedQueries/QueryLogDropping 告警，可补磁盘容量告警）。
2. **日级统计在大流量下延迟较高（WARN）**：范围索引修复已消除全表扫描，但单日 4184 万行的聚合仍需 ~45s。属 SQLite 单文件聚合的固有成本；如需亚秒级日统计，需预聚合表（写入时按小时桶累计）作为后续优化项。
3. **测试数据污染说明**：本机 UDP 压测（36 万次查询）写入了生产实例查询日志（约占当日总量 0.9%），随保留期自动清理，无需人工处理。
4. **`/api/v1/dashboard/top` 等聚合在更大时间跨度下的表现**：自定义范围已限制 90 天，90 天窗口在本数据量级下未实测（会非常慢），建议配合未解决问题 #1 的容量策略处理。
