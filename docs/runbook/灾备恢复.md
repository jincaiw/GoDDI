# 灾备恢复 runbook

> 适用范围：把一个 **GoDDI 实例**从 `goddi backup` 写出的归档恢复到**一台什么都没有的主机**上。
> 版本基线：v0.6.0（`workbuddy/impl-v0.6.0`，工作树基线 `d5b5fe3`）。
> 可执行形态：`scripts/w12c_restore_drill.py`。**本文的七个步骤与脚本同序、编号相同**——改一个就是改另一个。

---

## 一、这份 runbook 与它的可执行形态

文档容易被读成「大概是这样」，而灾备流程的每一步都必须在**真的没有源**的前提下成立。所以本文配了一个可重复执行的演练 `scripts/w12c_restore_drill.py`：它从仓库根目录跑，自己建实例、自己取归档、**真的把源删掉**，再在一台空主机上恢复并探活。它的退出码 0 表示「本文说的每一件事都成立」。

```bash
python3 scripts/w12c_restore_drill.py
```

依赖：`go`、`sqlite3`、`curl`（脚本会先检查后两个在不在，缺了直接退出 2 而不是跑到一半失败）。

**为什么需要它**：工作树里另有两个 `scripts/w12_snapshot_smoke_check.py`（73 项）与 `scripts/w12_mutation_check.py`（6 处变异）。它们都在**写归档的那台机器上**读归档——这就看不出任何「只有本机才有的路径」造成的依赖。演练补的正是这一块。

## 二、事实基础（读流程前先记住这些）

### 2.1 实例拥有三个库

| 存储 | 文件（默认位置） | DSN 来源 | 是否必需 |
|---|---|---|---|
| `control` | `<server.data_dir>/goddi.db` | `database.dsn` | **必需**（丢失即无法恢复实例） |
| `dnsdata` | `<server.data_dir>/dnsdata.db` | `dataplane.zone_dsn`，空则取 `data_dir/dnsdata.db` | 可选 |
| `leases` | `<server.data_dir>/leases.db` | `dataplane.lease_dsn`，空则取 `data_dir/leases.db` | 可选 |

`server.data_dir` 默认 `./data`。三个库全在数据目录下，是刻意的：**覆盖数据目录的备份就覆盖了数据面对「自己刚才在做什么」的记忆**。

### 2.2 归档只带库、配置和一个清单——**密钥材料不在里面**

- 归档扩展名 `.goddi-snap`，加密容器魔数 `GODDI-SNAP-ENC1`，整体分块 AES-256-GCM（1 MiB/块）。
- 密封用的材料是 `security.encryption_key`；**该键没配时会退回 `jwt_secret` 并打一条 warning**。
- 归档里**没有**这份密钥。这是格式的用意，不是遗漏：一个自带密钥的加密备份等于一个没加密的备份。
  → **密钥材料必须在归档之外单独保管**。丢了它，归档就打不开——见第五节第 5 条。

### 2.3 `goddi backup` 不需要停服务

它用 SQLite 的 `VACUUM INTO` 逐库复制：跑在**读事务**里，拿到的是「一个正被写入的数据库的单一瞬间」。所以可以在服务运行时取归档。（这一点由 W12-a 的 `TestASnapshotIsOneConsistentInstant` 用未提交写事务固定。）而 `restore --in-place` **必须停服务**，见步骤 5。

### 2.4 恢复前闸门的判据是「**本二进制自带的迁移上限**」，不是本机库

`goddi restore` 在写任何东西之前，把归档 manifest 里的 schema 版本与**本二进制 embed 的迁移上限**（`knownSchemaVersions()`）比较：

- 归档 schema **高于**本二进制 → **拒绝**（更旧的二进制读不了更新的 schema）。
- 归档 schema **低于**本二进制 → **接受**，下一次启动服务时迁移会把它前移。**这正是「把昨晚的备份恢复到一台已经升级过的实例上」这个最常做的事。**
- 归档含本二进制**没有迁移**的存储 → **拒绝**（判断不了就不放行）。
- 产品版本（`manifest.Version` vs `Version`）作为人类可读的第二信号；**版本不可解析时如实声明比较被跳过**（`dev`、`0.6.0-3-gabc` 这类 build），由 schema 承担判定。

> 它**不**与本机现有库比。与库比会在两个方向上错：新主机上还没有库，整段检查被跳过（**却不报错**）；而「恢复昨晚的备份」会被误拒。见 `docs/adr/0002-migration-expand-contract.md` 与 `cmd/goddi/restore_gate_test.go`。

## 三、恢复流程（与演练脚本同序）

### 步骤 1 — 把源实例建起来，并让它持有可识别的数据

*（演练动作；生产中对应「源还在跑，你打算开始做灾备」。）*

```bash
goddi migrate -c /etc/goddi/config.yaml     # 建库并迁移到本二进制支持的版本
goddi serve  -c /etc/goddi/config.yaml     # 起一次，让「装配」而不是脚本决定哪些库存在
```

**为什么必须真起一次服务**：`dnsdata` / `leases` 这两个数据面库是**服务装配时**创建的，不是 `migrate` 建的。只跑 `migrate`，归档里会缺掉它们——而那正是「恢复后才发现少了租约库」的成因。

演练在这里往控制库写一行标记（`system_settings` 表），用来在步骤 6 证明「回来的确实是源的状态」。

### 步骤 2 — 取归档，并把它放到**源实例之外**的地方

```bash
goddi backup -c /etc/goddi/config.yaml -o /srv/vault/goddi-$(date +%Y%m%d).goddi-snap
goddi restore -c /etc/goddi/config.yaml -i <归档> --verify
```

要点：

1. **`-o` 必填**，且拒绝覆盖已存在的文件（`O_EXCL`）。路径自己定——**不要放进 `server.data_dir`**，否则删源的时候一起没了。
2. 先确认归档是**密封**的：文件头就是 `GODDI-SNAP-ENC1`。演练直接读前 16 字节断言，不靠命令自述。
3. `--verify` **在任何东西被销毁之前**跑一次。它读 manifest、逐成员校验 SHA-256、报告归档里有什么、并报告「本二进制能不能用它」——**但 `--verify` 只报告闸门结论，不强制**（`--verify` 回答的是「这份归档完好么」，那是关于产物的问题）。强制发生在真正写东西的那两条路径上。
4. **在销毁源之前，把归档复制到源实例之外的介质**（异地/对象存储）。演练把归档放在与源**不同的顶层目录**，然后才进步骤 3。

### 步骤 3 — 销毁源实例：这一步之后没有回头路

*（演练动作；生产中对应「源真的没了」，或你正在做一次真实的演练。）*

```bash
# 演练里等价于 shutil.rmtree(src)
```

演练在这里真的把源目录删掉，并断言两件事：源不存在了、**归档还在**（因为它在源之外）。

**为什么非要真删**：不删源，「恢复到新实例」这句话就没有被验证——任何残留的本机路径都会替你兜底，而你永远不会知道。

### 步骤 4 — 目标主机：先确认它**确实什么都没有**

```bash
goddi migrate -c /etc/goddi/config.yaml --status
```

在一个从没跑过的目标主机上，这份报告会明说：

- 三个库都报「**数据库尚未创建**」；
- 有**待应用**的迁移（「待应用合计：N」，N 不为 0）；
- 目标数据目录里**没有 `goddi.db`**。

`--status` 会先 `os.Stat` 再决定开不开库：**打开一个不存在的 SQLite 路径就会创建它**，而一个「为了报告状态而把库建出来」的命令，回答的已经是另一个问题了。它还**不施加任何 PRAGMA**（`journal_mode` 会写文件头）。→ 跑完 `--status` 之后，三个库文件必须仍然不存在。

### 步骤 5 — 恢复到目标主机

**先停服务。** 然后：

```bash
goddi restore -c /etc/goddi/config.yaml -i <归档> --in-place --yes
```

`--in-place` 的语义，按发生顺序：

1. 把归档解到**临时目录**，整包读完、每个成员比对完，才开始动本机的库（半失败不会留下半个解包目录）。
2. 判定闸门（见 2.4）。判不过就**在写任何文件之前**退出。
3. **留存替换前副本**——但**只在真的有库要替换时**：
   - 有库 → 写 `data/backups/prerestore_<时间戳>.goddi-snap`，输出「替换前已留存当前数据库副本：…」；
   - **一台什么都没有的主机 → 输出「目标主机上没有任何库，没有需要留存的替换前副本」**，然后继续。
4. 逐个替换数据库文件：副本落在目标**同目录**再 `Rename` 就位（原子、不跨文件系统），并连同 `-wal` / `-shm` / `-journal` 一起清掉。
5. 明说「**归档中的配置文件刻意未应用**」——它描述的是归档来源主机。

> **第 3.2 步是「恢复到新实例」唯一不能出错的地方，而它曾经就是错的**：替换前副本曾**无条件**取，而 `snapshotTargets` 把控制库标为必需——于是在一台从没跑过的主机上，命令在替换任何东西之前就失败，报一个操作者从来没有过的库「不存在」。空主机是这条命令最要紧的地方，却曾是它唯一跑不起来的地方。（见 `cmd/goddi/main.go` 的 `existingStores` 与其注释。）

关于 `--in-place` 的边界：

- **归档不含的库，本机保持原样**，不会被清空——「归档里没有租约库」意思是源主机没有，不是要删掉本机的。命令会打印一行「注意：归档不含 X 库，本机的 Y 保持原样」。
- 它**不跑迁移**。schema 由下一次启动服务前移——那是升级走的同一条路径，因此是被真正验证过的那条。

### 步骤 6 — 核对恢复结果：文件、配置、schema 三样都要对

```bash
goddi migrate -c /etc/goddi/config.yaml --status     # 期望：三个库都「无待应用」
goddi restore -c /etc/goddi/config.yaml -i <归档> --into /tmp/unpacked   # 单独解一份，用于比对
```

| 核对项 | 怎么核对 | 期望 |
|---|---|---|
| **文件字节** | 把恢复出来的库与归档的**同名成员**（`/tmp/unpacked/db/<name>.db`）比 SHA-256 | **相等** |
| （同上，反向） | 与**源的活文件**比 SHA-256 | **必然不等**——见下 |
| **完整性** | `sqlite3 <库> "PRAGMA integrity_check"` | `ok` |
| **残留** | 数据目录里不应再有 `-wal` / `-shm` / `-journal` / `.restore-new` | 一个都没有 |
| **配置** | 目标 `config.yaml` 的 SHA-256 | **与本机恢复前一致**（归档里的配置没被应用） |
| **schema** | `--status` 报的「已应用 N / 本二进制最高 M」 | N == 归档 manifest 声称的版本 |
| **数据** | 步骤 1 写的标记行还在不在 | 在 |

**为什么「等于归档成员」与「不等于源活文件」两条都要断言**：归档成员出自 `VACUUM INTO`，那是一个**压实的单文件、回滚日志模式**；而源的活文件是**被写过的 WAL 库**。**正确的恢复本来就会让两者不同**——只断言「等于源活文件」会在一次正确的恢复上失败。演练两条都断言。

**比较必须在任何东西打开这些库之前做**：一旦有进程（哪怕是探针）碰过，就会建出 `-wal` / `-shm`。

### 步骤 7 — 把恢复出来的实例真正启动起来并探活

```bash
goddi serve -c /etc/goddi/config.yaml
curl -s -o /dev/null -w '%{http_code}\n' http://127.0.0.1:<http_port>/health
curl -s -w '\n%{http_code}\n'              http://127.0.0.1:<http_port>/ready
```

要点：

- **`/health` 与 `/ready` 都要轮询到 200 再停**，不要采样一次。监听 socket 比 handler chain 更早接受连接，单次请求完全可能被一个**正在正常启动**的服务拒掉。
- `/health` 永远 200（存活），`/ready` 才是「能不能服务」。`/ready` 只在 `role=all|control` 存在。
- **别让探针变成空转**：真正要断言的是日志里出现了数据面就绪的实质证据，而不只是「HTTP 200」。演练断言 `dataplane: readiness ok` 出现在日志里——即数据面**从恢复出来的库前移到当前状态**，而不是「因为什么都没检查所以健康」。
- 另断言：进程**优雅退出**（日志有 `GoDDI stopped gracefully`）且**没有 panic**。

> **DHCP 与探活的坑**：`/ready` 变 `failing` 的一个常见原因是 `dhcp_listener_failed_to_start`——非特权环境绑不了 `udp4 :67`。这**与恢复无关**。演练因此让**源**开 DHCP（好让它有租约库可归档）、**目标**不开；否则 `/ready` 的断言就变成一句关于运行环境的真话，而不是关于恢复的。

## 四、备份排期（演练不覆盖，但**必须**单独做）

**本产品不内置备份排期。** 备份不会自己发生——需要运维侧配置 cron / systemd timer / 外部调度：

```cron
# 每天 02:17 取一份全量归档到异地的 vault
17 2 * * * /usr/local/bin/goddi backup -c /etc/goddi/config.yaml \
            -o /srv/vault/goddi-$(date +\%Y\%m\%d).goddi-snap
```

三条约束：

1. **归档必须落到源实例之外**（见步骤 2）。放本地 = 与源同生共死。
2. **密钥材料必须单独保管**（见 2.2）。放进同一个 vault 等于没加密。
3. **归档会累积**：本命令**不做保留期清理**。保留策略由运维侧实现（例如「留 7 日 + 4 周」）。

## 五、这份 runbook **刻意不声称**的事

每一句「不声称」都对应一个**没有被验证**的断言，写在这里是为了不让下一个人把它当成已成立的事。

1. **没有真正的「更新的二进制」**。闸门的「归档比本二进制新」方向是靠**一份 manifest 说谎的归档**驱动的（只替换 `manifest.json`，成员摘要仍全对），走的是同一条代码路径、同一形状的输入，但**不是**第二个 build。
2. **`--into` 在闸门判定前就已经解包**。`ReadSnapshot` 单趟完成「校验 + 解包」，所以被拒绝的 `--into` 仍会在你指定的目录留下文件（`--in-place` 走临时目录、随 `defer` 消失，不受影响）。拒绝信息里明说了这一点，但**没有阻止**。
3. **`goddi backup` 不会喂那两条备份告警**。`goddi_backup_last_success_timestamp_seconds` 与 `goddi_backup_jobs_total` 的生产者是**管理面**的备份管理器（读控制库 `backup_jobs` 表）；而 CLI `goddi backup` 用 `CreateSnapshot` 写文件，**不写 `backup_jobs`、不注册任何指标**。因此：
   - 按本 runbook 手工跑 `goddi backup` 之后，**不要以为** `GoDDIBackupStale` / `GoDDINoSuccessfulBackup` 会自动恢复——它们看的是管理面那张表。
   - 反过来，只用 CLI 排期、从不用控制台/API 的备份功能，这两条告警会一直报（`GoDDINoSuccessfulBackup` 在运行满 7 天后触发）。要用告警看住 CLI 排期，需要**外部**监控归档文件的年龄，或改走管理面排期。
4. **本工作树没有 CI 接线**。ADR 0002 的 expand-contract 检查器（`internal/database/migration_contract_test.go`）**只在跑测试时生效**。所以「以后没人能提交破坏性迁移」这个承诺，目前依赖「有人跑测试」，不是一道自动闸门。
5. **密钥材料若丢失，本仓内无法恢复**。演练**刻意不排练**这一步：归档是密封的、密钥不在里面，正是格式的用意；也没有任何东西能在本仓内把它从别处找回来。
6. **DHCP 监听器未在演练中验证**。见步骤 7 的说明：非特权环境起不了 `udp4 :67`，这是运行环境的事实，与恢复无关，所以被排除在断言之外。
7. **未做长时间运行验证**：恢复后只探活，没有让恢复出来的实例在负载下跑一段可观时间。
