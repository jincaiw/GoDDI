# 耐久与容量画像 — W14-d / W14-e

一句话：**把「断电会不会丢已 ACK 的绑定」和「2 万租约下这个系统长什么样」各自量出来，并把不能声称的部分写在结论旁边。**

ADR 0001 的容量口径是 **≤2 万租约、双节点 4C/8GiB、租约库 WAL + `synchronous=FULL`**。实施计划的退出条件对这两项的要求是：

> **断电/存储耐久测试与进程重启测试分开记录**；未做则标未验证。
> 长稳与容量测试在**带持久提交和 HA 配置**下执行；未执行前不发布容量数字。

本文档按这两句组织：第一节只谈耐久，第二节只谈容量，第三节记录本轮抓到的缺陷，第四节列脚本与变异校验，第五节列**未验证的清单**。

---

## 一、耐久：两种「停机」分开记录

两者不是同一个主张，因此**从不合并成一个数字**。

| | A. 进程重启（SIGTERM，有序停机） | B. 断电模拟（SIGKILL，无 defer、无末次 checkpoint） |
|---|---|---|
| 载体 | `goddi serve` + `goddi ha degrade`（真二进制） | 同左，外加 `internal/dhcp/lease` 的真子进程写入方 |
| 断言 | 已提交的算子决策、它的理由、以及「重启后的服务按它运行」 | 库可读、`PRAGMA integrity_check = ok`、决策与理由都在、write-ahead log 仍在 |
| 结果 | **成立** | **成立** |

### A 节做了什么

真二进制起一个 `role=dhcp` 的主节点 → `goddi ha degrade --confirm --reason "…"` → 等**运行中的服务**在日志里采纳（`an operator has approved running without a second copy`）→ SIGTERM → 再起一个进程 → 从**只读路径**（`goddi ha status --json`，`mode=ro`、不迁移）读回。

三个断言：`state == primary-degraded`、`degraded == true`、`redundancy_known && !redundant`。它们都由同两行 meta 推导，所以一个半写成的决定会让三者互相矛盾——这正是崩溃测试该拒绝接受的东西。

理由（`degraded_reason`）也逐字比对：`Degrade` 把标记和理由写成**两条独立语句**，只检查布尔值的重启测试会漏掉只写了第一条的情况。

### B 节做了什么

同 A，但用 **SIGKILL** 结束。

- kill 之后立刻断言 `leases.db-wal` **存在且非空**——这是「崩溃一致性 ≠ 耐久性」最有说服力的物证：数据是从一份**从未被 checkpoint 的 WAL** 里恢复的，而不是从落盘的页里。
- 从只读路径读回，三个推导互相一致；理由逐字比对。
- 用**系统 `sqlite3`（独立读者）**跑 `PRAGMA integrity_check` → `ok`。产品若能读出一个系统 SQLite 认为损坏的文件，上面的读回就是错的证人。
- 重启服务，日志里必须出现 `"state":"primary-degraded"`。

### B 的写入方：真子进程，真 SIGKILL

`internal/dhcp/lease/durability_test.go` 里的写入方是本测试二进制**用环境变量重新进入自己**（`GODDI_W14_LEASE_WRITER=1`），打开的就是产品用的 `dataplane.Open`，写的就是产品的 `lease.Manager`。父测试等它提交到 50 / 300 / 900 条，然后 SIGKILL。

写入方**在提交返回之后**才往日志追一行、并且从不 sync：日志只需要被父子之间看见，而交给 `write(2)` 的字节在进程死后仍在页缓存里。不 sync 是为了让写入够紧，kill 才落得进一次写中间。

两条断言方向相反，缺一不可：

| 断言 | 失败意味着 |
|---|---|
| 库里的行 **⊇** 日志里的「已提交」 | 已 ACK 的绑定丢了——客户端拿着一个服务器不记得的地址 |
| 库里的行 **≤** 已提交 + 1（最多一条在飞） | 库里有服务器**从未签发过**的绑定：事务回滚只发生在内存里，或一条将来掉电会被收回的行读成了正式绑定 |

实测（三次）：68 条已提交 / 69 行、326 / 326、905 / 906。那个 `+1` 在两次运行里真的出现了，说明这个上界不是摆设。

### 存储层注入

两种「存储说不行」，断言同一条不变式：**只有权限真的进了库，命令才可以打印成功**。

| 注入 | 做法 | 结果 |
|---|---|---|
| 文件系统只读 | `leases.db`、`-wal`、`-shm` 全部 0444、目录 0555（只改主库文件没用：WAL 模式下写落在 `-wal` 上） | 命令非零退出并说明原因；权限**没有**进库 |
| 存储层拒绝该表 | 用系统 `sqlite3` 在 `dataplane_meta` 上装 `BEFORE INSERT … RAISE(ABORT)` | 命令非零退出、带上存储层自己的原话；权限**没有**进库；去掉触发器后同样的命令成功 |

注入本身被验证过有牙齿：把 `Degrade` 两处 meta 写入的错误都吞掉（打印成功但库里没有），进程级脚本报出 `the command printed success but the permission is not in the store`。
只吞第一处**不报错**，而且不该报错——第二条写入仍然失败，命令仍然拒绝，不变式成立。这条「擦肩而过」写进了变异脚本的注释。

### 一个观察（不是缺陷）：WAL 库只读时连只读报告都读不出来

C 节第一次尝试时，`goddi ha status` 在文件只读的情况下自己失败了：
`dataplane: connecting to the lease store: attempt to write a readonly database (1544)`（`SQLITE_READONLY_RECOVERY`）。

原因是 WAL 库的只读打开仍需要写权限来恢复日志。这是 SQLite 的规则，不是一个可以在这里修的东西，但它是**运维要知道的**：把租约库所在目录挂成只读（例如挂一个快照）之后，`goddi ha status` 也读不出来，不只是写不进去。

## 二、容量与长稳画像（分钟级，带持久提交与 HA）

脚本：`scripts/w14_capacity_profile.py`。两个真进程结成一对（主备），主库载到 ADR 的容量口径，然后分三节测量。

**本机画像：10 核 / 16 GiB**。ADR 的目标画像是双节点 4C/8GiB——**不是同一台机器**，所以下面的数字是「在比目标宽裕的机器上的形状与量级」，不是目标画像上的承诺。

### 数字

| 项 | 实测 | 说明 |
|---|---|---|
| 20,000 条租约占用 | **14.1 MiB**（738 字节/租约） | 库 + wal + shm；对应 1 GiB 的额度上限，余量两个数量级 |
| `goddi ha status --json` 在 20,000 条上 | **10–12 ms** | 只读打开，三次取最小 |
| **单行**同步提交（一次提交＝一次确认的耐久成本） | 中位 **0.32 ms**，最差 0.68–0.96 ms → **≈3,100 次/秒** | 200 次采样。这才是 ACK 的形状 |
| **备机从空到追平 20,200 条** | **1.3–1.4 s** | HA 契约刻意没有增量追赶，每次重连都是全量快照；20,200 行在一个 32 MiB 上限的帧里 |
| 批量同步提交（500 行/事务） | **30,403 行/秒** | 与上一行不是同一个测量，合并会掩盖操作员真正感受到的那个 |
| 常驻内存（主 / 备） | 主 ~86 → 31 MiB；备 ~80 → 15–37 MiB（全序列已打印） | 首个采样落在快照应用期间，是全run的最高点；只报首尾会把它描述成「释放了内存」 |
| 稳态期间 | 24 批 × 500 行，无一失败；两个进程都无 `database is locked` / `SQLITE_BUSY` | 第二个进程持续对同一个库做 `synchronous=FULL` 提交 |
| 库内行数（独立只读读取） | 32,200 = 起始 20,200 + 写入 12,000 | 速率确实是在写这个库 |

### 上界（会失败的断言，不是描述）

- 单次同步提交最差 > 1000 ms → 失败（「客户端等了一秒才拿到地址」）
- 任一进程在 120 秒稳态内增长 > 256 MiB → 失败（**在证明不是泄漏之前就是泄漏**）
- 稳态结束后库内行数必须等于「起始 + 写入」→ 否则上面的速率在测别的东西
- 快照行数必须等于主库实际行数（主备两侧各自断言，备机侧用独立只读读取）
- 主备任一日志出现 `database is locked` / `SQLITE_BUSY` / `panic` → 失败

### 夹具为什么把 scope 同时写进两个库

scope 是控制面配置，数据面把它是**复制**下来的。第一版夹具只把 scope 写进租约库，主机立刻每秒报一次
`dataplane: copying lease cap-0 up: constraint failed: FOREIGN KEY constraint failed (787)`。
那不是一个可以忽略的噪声——见下面第三节第 2 条。夹具现在按真实部署的样子建：scope 控制库和本地库都有。

## 三、本轮由耐久与容量画像抓到的真缺陷

### 1. 分配路径的代价随池子被占用的程度增长（已修）

`lease.Manager.FindAvailableIP` 原来是**逐个候选地址发两条 EXISTS 查询**：

```go
for { … m.db.QueryRow(availabilityQuery, …) … ip = nextIP(ip) }
```

| | 2 万租约、/16 池 | 查询次数 |
|---|---|---|
| 修复前 | **310 ms** | 每个已占用地址 2 次 → ≈40,000 次 |
| 修复后 | **13 ms** | 1 次 UNION + 一次排序 |
| 池子全满（65,534 个候选） | ≈1 s | ≈131,000 次 |

它在 **DISCOVER 路径**上，而且 `Server.reserveAddress` 最多重试 5 次——一次竞争可以让一个客户端等上 1.5 秒。代价的形状还是反的：池子越满，下一个客户端越慢。

修法：把「被占用的地址集合」一次读出来（`dhcp_leases` 中处于 `heldStatuses` 的行 ∪ `dhcp_reservations` 中 `enabled = 1` 的行），排序后走一遍找第一个空隙。`heldStatuses` 仍是唯一来源（仍走 `heldStatusPlaceholders()`），答案逐地址不变。

两个证明：

- **等价**：`TestTheFirstFreeAddressIsTheOneBruteForceWouldFind`——60 组随机状态，期望值由 Go 里根据「种了什么」算出来，绝不查库。**不阻挡的状态也在里面**：`expired`、`released`、`enabled = 0` 的预约都不是「被占用」。一个把「有行」当「被占」的实现能过更简单的测试，过不了这个。
- **形状**：`TestTheCostOfAllocatingDoesNotDependOnWhereTheGapIs`——两个库装**同样多的 20,000 行**，一个空隙在第一个候选、一个在 20,001 个之后。一次查询加排序的代价在两者相同；逐候选探测差四个数量级。实测 **15 ms vs 14 ms**。

> 一个被实测否掉的守卫：先写的是「2 万不能比 2 千贵十倍」。装上旧实现实测比值 **6.7**（43 ms vs 287 ms），低于任何共享机器上敢设的阈值——比值**根本分不开这两种形状**，因为两者都随池子增长。换成「空隙在哪」才分得开。这条留在代码注释里，免得下一个人重新写一遍那个行不通的守卫。

### 2. 一条永远推不上去的租约，会永久卡住整个上行队列（**2026-09-11 已修**）

`dataplane.Replicator.Push` 按批取待上行租约，逐行 upsert；**第一行出错就 `return`**，事务回滚，所有行留在队列里。复现：本地库里有 `scope_id` 在控制库不存在的租约（外键拒绝），主机日志于是**每秒一条**：

```
dataplane: pushing lease changes up failed; it stays queued
  error: dataplane: copying lease cap-0 up: constraint failed: FOREIGN KEY constraint failed (787)
```

后果有三层，第三层最重：

1. 队列头阻塞——**一条坏行让后面所有行永远上不去**，控制台就此停止反映任何租约变化；
2. `metrics.RecordDBError()` 每秒 +1，`GoDDIDBErrors`（10 次 / 10 分钟）告警被**永久点亮**；
3. 不可达吗？**可达**。至少两条路：① 控制库从**早于某个 scope 的备份**恢复（W12 的灾备流程就是这么用的），数据面的租约仍在；② 运维用脚本/修复工具直接写租约库（本轮画像的 C 节就打印了这条边界）。

DNS 的 outbox 已经有「超限转 `failed` 保留可见」的先例，上行租约队列没有对应机制（`dhcp_lease_dirty` 表只有 `lease_id / deleted / queued_at`，**没有尝试计数**）。

**这是策略决定，不是缺陷修补**：跳过后标 `failed`、直接丢弃、还是有界重试后告警，选择不同运维含义也不同。按本项目「非小型改动先确认决策点」的约定，本轮只记录与复现，**未改**；建议与推荐做法见交付说明。

**2026-09-11 决定与实施（六条队列，不止租约队列）**：`Push` / `PushEvents` / `PushZoneSerials` / `PushLogs` /
`PushAuditLogs` / `PushRecords` **共用同一形状**，所以一起改，而不是只修租约那一条：

- 迁移 `internal/dataplane/migrations/005_marker_retry_state.sql` 给六张标记表各加 `attempts` /
  `next_attempt_at` / `last_error`（全部 `ADD COLUMN`，符合 ADR 0002 的 expand-contract）。
- 逐行隔离：被拒的行记 `pushFailure` 并 `continue`，**成功的行照常进 `done` 并清标记**；提交后先 `clearMarkers`
  再 `recordPushFailures`（顺序承重：还欠着的行不能丢掉自己被拒的记录）。
- 有界退避**且没有终态**：1s → 5s → 15s → 1m → **5m 上限**。理由写在迁移注释里：本版本**没有任何算子动作
  能复活被写销的行**，一个 `failed` 终态只是把「队列卡住」这种静默失败换成「行悄悄不再投递、只能手工改库」
  的另一种静默失败；退避的代价（病因修好后最多等 5 分钟）是明确的、可见的。
- **不改触发器**：十一个写标记表的触发器说的是「这行变了、又欠了」，重试状态说的是「投递怎么样了」——
  把 `ON CONFLICT` 子句改成顺带重置计数会把这两件事耦合起来，且下一个加标记表的人必须知道这件事。
- `next_attempt_at` 的「现在到期」用 **NULL** 表达并可空无默认（`ALTER TABLE ADD COLUMN` 的默认值必须是常量），
  过滤条件写成 `d.next_attempt_at IS NULL OR julianday(d.next_attempt_at) <= julianday('now')`——
  SQLite 的 `julianday(NULL) <= julianday('now')` 是 **NULL 而不是 true**，依赖它的过滤会跳过表里每一行
  却报「积压为 0」。
- 可观测：`Refused()` → `Status.RefusedRows` → `/ready` 的 `change_refused` reason →
  `goddi_dataplane_refused_changes`（label 只有 `plane`：它由十秒 tick **只在内存里**读，每队列计数意味着
  每 tick 六次 store 读）→ `/api/v1/system/dataplane` 的 `refused_rows` → 新告警 `GoDDIDataPlaneChangesRefused`
  （>0 持续 5 分钟，warning；与「积压」的区别、退避阶梯与上限、最常见病因（向下同步还没落地）会自愈，
  都写在告警描述里）。
- `PushZoneSerials` 的一处**行为变更**：原来「serial 读不出来就清标记」（注释自称「清掉它就不能永远挡队列」），
  现在改为记为拒绝——那一行说的事实是「本机 serial 与控制库已分叉」，而一个会静默丢掉这个的队列，
  在它确实报出的行上也不可信。
- 验证：`internal/dataplane/push_retry_test.go` 六个用例；`w14g_push_isolation_mutation_check.py`
  **8/8 + `TREE-CLEAN`**（含「队列清单里表名打错」「键列名写错」这两处**面向未来加第七张表**的变异）。

## 五、不能声称的（与结论同等重要）

1. **真实掉电未验证。** kill -9 结束的是进程，不是内核：写入方交给 `write(2)` 的每个字节仍在页缓存里，恢复靠的是没有被 checkpoint 的 WAL（B 节已断言它在崩溃后仍在且非空）。
   `synchronous=FULL` 唯一的机器证据是打开后的**读回校验**（`TestOpenAppliesTheDurabilitySettingsThatMakeAnAckHonest`）；把它降到 0 之后崩溃演练**照样通过**——这一点由变异脚本作为「预期不被捕获」显式记录，不是猜测。
   要真正验收「掉电不丢已 ACK 的绑定」，需要在真机上切电，本工作树做不到。
2. **客户端的 ACK 未在真实 UDP 会话上验证。** 本机非特权且 :67 已被占用，DHCP 监听器绑不上（进程如实记录并继续）。所以「租约写不进去就不发 ACK」只到存储层为止：语义由 `TestNoAckWhenTheLeaseCannotBeWritten` 与 `TestAWriteTheStoreRefusesIsReportedAndLeavesNothing` 钉住，**没有一条报文在线上被拒绝过**。
3. **不是 DHCP 客户端压测。** 画像里的写入直接对租约库做同步提交，测的是存储层在持久提交下的吞吐与争用，不是「每秒能答复多少客户端」。没有 DNS 查询性能数字。
4. **不是 24 小时长稳。** C 节 120 秒，足以看到泄漏的形状和 `SQLITE_BUSY`，不足以声称「三天后不会劣化」。内存判定是增长上界，不是无泄漏证明。
5. **单次运行。** 所有数字取自一次运行，没有重复取分布；同机器上跑别的会改变它们。
6. **备机追平只有一个规模点。** 快照耗时对行数是否线性**没有测**，「4 万条约两倍时间」是推断。
7. **跨进程直接写库不进镜像。** 画像的 C 节打印了两侧行数（备机停在 20,200，主机到 32,200）。这是刻意的边界：租约的唯一合法写者是 `lease.Manager`。
8. **硬件不同。** 本机 10 核 / 16 GiB，目标 4C/8GiB。要在目标画像上**发布**容量数字，必须在目标画像上跑。
