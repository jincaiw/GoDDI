# ADR-0002：迁移的 expand-contract 规范与回滚单位

- 状态：**已接受**（2026-09-10，W12-b 实施期确定）
- 日期：2026-09-10
- 基线：`d5b5fe3`（v0.5.2）
- 实施工作树：`workbuddy/impl-v0.6.0`
- 依据：W12-b 交付要求（迁移规范 + `goddi migrate --status` + 恢复前闸门）
- 机器检查：`internal/database/migration_audit_test.go`（`TestMigrationsFollowExpandContract`，覆盖 R1–R4）

## 背景

到 W12 为止，本仓共 28 个迁移：控制库 `migrations/001`–`024`，数据面 `internal/dataplane/migrations/001`–`004`。它们全部由人工编写，此前只有一条成文规则——「goose 触发器必须包 `-- +goose StatementBegin/End`」——那是一条**语法**规则。没有任何规则约束一个迁移**在语义上允许做什么**。

缺这条规则的后果不是编译失败，而是**发布之后才发现**：

- 一次发布里同时「停止写旧列」和「删掉旧列」，那么回滚这版二进制就会失败——旧代码查一个已经不存在的列。现场能选的只有两条：前滚（可能正是出问题的那版），或者从备份恢复并丢掉这段时间的写入。
- 一次发布里把大表回填和加列写在同一个迁移里，回填耗时随数据量增长，而它跑在**服务启动期**。数据量大到一定程度，升级窗口就变成了「服务起不来」。

这两条都不是理论风险，而是这类 schema 管理的标准失败模式。本 ADR 把它们变成规则。

## 决策

### 迁移的分类

每个 `-- +goose Up` 里的语句归入四类之一：

| 类别 | 语句形态 | 语义 |
| --- | --- | --- |
| **ADD** | `CREATE TABLE` / `CREATE (UNIQUE) INDEX` / `CREATE TRIGGER` / `CREATE VIEW` / `ALTER TABLE … ADD COLUMN`；只写进本迁移刚建的表与列的 `INSERT` | 只增不减。旧二进制读不懂新列/新表，但会忽略它们 |
| **REPLACE** | `DROP <object>`，且同一 `Up` 内随后 `CREATE` 同类对象 | 替换一条规则（索引/触发器/视图）。数据面无损 |
| **BACKFILL** | 数据写入：`UPDATE <t> SET <col>`、`INSERT … SELECT`、`INSERT … VALUES`、`DELETE FROM <t>` | 写的是**数据**，不是形态 |
| **CONTRACT** | `DROP TABLE` / `DROP COLUMN` / `RENAME TO` / 收紧既有列的约束 | 使旧二进制读不了或写不进 |

`DELETE FROM` 划入 BACKFILL 而非 CONTRACT：它删的是**行**，不是旧二进制依赖的**列**。旧二进制仍能运行，只是行没了——这是数据变更，不是 schema 变更。

唯一索引加在**既有列**上仍算 ADD（它不丢数据），但它会开始拒绝此前能通过的写入。这一条有单独规则（R5）。

### 规则

- **R1** 每个迁移必须同时含 `-- +goose Up` 与 `-- +goose Down`。
- **R2** `Up` 内不得出现 CONTRACT 语句。破坏性动作只能出现在**后续发布**的迁移里；那时已没有任何受支持的二进制读旧形态。
- **R3** `Up` 内每个 `DROP <object>` 必须与同一 `Up` 内一条同类 `CREATE` 配对（先删后建的同迁移替换）。没有配对的删除就是 CONTRACT。
- **R4** `Up` 内的回填只能落在**本迁移刚新增的列**上。判据只覆盖 `UPDATE <t> SET <col>`——**插入和删除行不在 R4 之内**。理由：往一张表里多插几行、少删几行，不改变 schema 的形态，旧二进制读到的是「行多了/少了」，不是「读不懂」。R4 要拦的是那种**改写已有列含义**的回填，因为那才是升级不可逆的地方。
- **R5**（**人工评审项，本 ADR 不机器检查**）在既有列上新加唯一约束的迁移，必须在注释里给出约束失败时的诊断查询。约束失败是**故意**的——它意味着 schema 与数据已经不一致——但运维必须能从报错里查到是哪几行。

### 为什么

**回滚的单位是二进制，不是迁移。**

这条是全部规则的根。一次升级出问题，运维手上唯一的动作是**换回旧二进制**。要让这个动作成立，新二进制留下的 schema 必须仍被旧二进制读得懂：加东西安全（旧读者忽略），删东西不安全（旧读者查一个不存在的列）。

goose 的 `Down` **不能**替代这条规则。SQLite 的 `ALTER TABLE … DROP COLUMN` 会重写表，`Down` 能把列加回来，但**加不回值**。也就是说：

> `Down` 在 SQLite 上恢复的是**结构**，不是**数据**。「`Down` 存在」不等于「这次改动可以回滚」。

这条决定了 R2 不是可选项。同时也说明了为什么本仓的 `Down` 仍然要写全（R1）：它是**结构**层面的逃生门，能在「换二进制」的同时省掉手工改 schema；它不是数据层面的逃生门，数据层面的逃生门是 `goddi backup`（见 W12-a）。

### 当前状态（如实记录）

对 `migrations/001`–`024` 与 `internal/dataplane/migrations/001`–`004` 逐语句分类后：

- **R1**：28/28 通过。
- **R2**：28/28 通过。`Up` 里**没有**任何 `DROP TABLE` / `DROP COLUMN` / `RENAME TO`。所有 `DROP TABLE` / `DROP COLUMN` 只出现在 `Down` 里。
- **R3**：唯一含 `DROP` 的 `Up` 是 `017_dhcp_lease_offered_state.sql`——`DROP INDEX idx_dhcp_leases_scope_ip_active` 与 `CREATE UNIQUE INDEX idx_dhcp_leases_scope_ip_held` 在同一 `Up` 内，是真替换。它写在本 ADR 之前，**恰好**合规，不作例外记录。（另：`DROP INDEX` 只删索引定义，索引可从表数据重建，所以它本身也不是数据破坏。）
- **R4**：唯一含 `UPDATE` 回填的是 `020_ipam_kernel.sql`，两条 `UPDATE` 分别写 `ipam_addresses.space_id` 与 `ipam_history.space_id`，两列都由该迁移自己刚加，通过。除此之外的行写入都不在 R4 判据内：`022` 往 `021` 建立的 `dataplane_revision` 里插入 `ddns` / `leases` 两行种子，数据面 `001`–`004` 各自插入种子行。
- **R5**：`020` 在注释里给出了 `SELECT ip_address, COUNT(*) … GROUP BY space_id, ip_address HAVING n > 1` 的诊断查询，符合。

**因此：写下这条 ADR 时，仓库是合规的。它的价值在于约束未来，而不在于修过去。** 这一点必须说清楚，否则下一个人会以为规则是「对既有代码的形式化描述」而按既有代码去理解规则。

### 检查器自身的两个坑（写给下一个写检查器的人）

`TestMigrationsFollowExpandContract` 在写成的过程中**误报过两次**，两次都是解析顺序的问题，而不是迁移的问题：

1. **按换行切语句**把多行的 `CREATE TABLE (…)` 切成碎片，列定义被报成「不认识的语句」。SQL 语句的边界是分号，不是换行。
2. **先去分号、再去注释**：注释里出现分号（例如「a trigger body contains one; that is why it is wrapped」）会把注释切成两半，而分号之后那半句**没有 `--` 前缀**，于是被当成 SQL。`024` 与数据面 `001` 都撞上了这条。正确顺序是**先去掉注释，再切语句**。

这两条记在这里而不是只留在 commit 里，因为它们不是「一次性的调试过程」，而是任何按行解析 SQL 的检查器都会再犯的错。

### 尚未覆盖

- **回填耗时没有量化判据。** R4 管的是「回填落在哪一列」，不管「回填要扫多少行」。从大表批量复制的 `INSERT … SELECT`、或对全表 `UPDATE` 的耗时随数据量增长，而它跑在**服务启动期**——数据量大到一定程度，升级窗口就变成「服务起不来」。当前最大表规模（≤2 万租约，见 ADR-0001）下可接受；表规模上一到两个数量级后这条需要重审。
- **R5 不机器检查。** 上面的检查器查不了「诊断查询是否真的可用」。它只保证迁移仍存在、结构仍合规。
- **检查器只解析 `Up`。** `Down` 里出现破坏性语句是正常的——回滚本来就要删东西——所以 `Down` 不受 R2 约束，也因此不在检查范围内。
- **检查器不解析块注释与跨行字符串。** 遇到 `/* */` 或以未闭合字符串结尾的行会**直接拒绝**并要求改写，而不是猜。这会拦住一类合规的迁移，是刻意的取舍：宁可要求改写，也不要静默误判。
- **规则只覆盖 SQL 文本。** 一个迁移可以合规地让**代码**依赖一个尚未回填的列。这属于代码评审，不属于本 ADR。
