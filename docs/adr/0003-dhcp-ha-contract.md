# ADR-0003：DHCP 高可用的故障契约（单写热备）

- 状态：**已接受**（2026-09-10）
- 日期：2026-09-10
- 基线：`d5b5fe3`（v0.5.2）· 实施树 `workbuddy/impl-v0.6.0`
- 上游：ADR 0001 的 **INV-4（围栏先于接管）**、**INV-5（恢复以 ACK 集合为准）**、**INV-6（降级必须显式）**，以及决策 2（接受无围栏时暂停新租约；默认严格双副本；不引入 etcd/Redis 见证）

---

## 背景

ADR 0001 把 HA 的三条不变量写成了规则，但没写实现形态。落地前必须回答四个问题，每一个答错都会产出一个**看起来在 HA、实际不保证任何东西**的系统：

1. **复制走哪条通道**？现有复制全部经控制库中转（DHCP 面 → 上行推送 → 控制库 → 下行同步）。ACK 在客户端的关键路径上，如果确认也要经控制库，INV-3（控制面故障不中断数据面）当场失效。
2. **「备持久确认后 ACK」到底确认什么**？确认「收到了报文」和确认「已持久化」是两件事，而只有后者能让客户端收到 ACK 之后断电不丢地址。
3. **心跳超时能不能 promote**？不能（INV-4），双节点无法区分「对端宕机」与「网络分区」。那水位用什么？
4. **「暂停」时对客户端说什么**？不说会怎样，比说错更值得先想清楚。

---

## 决策 1：复制走**对端直连通道**，不经控制库

**规则**：primary 与 standby 之间有一条直连的复制通道（`dhcp_ha.listen_addr` ↔ `dhcp_ha.peer_address`），承载租约事实与水位。控制库**不在**这条通道上。

**理由**：ACK 在客户端的关键路径上。若确认要经控制库，则控制库故障 → 确认失败 → 不 ACK → **控制面故障直接中断 DHCP 服务**，正是 INV-3 禁止的。数据面之间的事实复制不应依赖低频的运维路径。

**代价（如实记录）**：多了一条需要运维放通、需要认证、需要单独观测的通道。它只在 `dhcp_ha.enabled = true` 时存在；默认关闭时**不监听任何端口**，单节点行为与本 ADR 之前完全一致。

---

## 决策 2：作者唯一 —— 备是纯镜像，永不自行授权

**规则**：**primary 是租约事实的唯一作者**。standby 只应用 primary 发来的租约变更，**绝不**自行创建、延长或释放租约；standby 上不跑 DHCP 监听器，不响应客户端。

**推论（本 ADR 的承重结论）**：**standby 的内容永远是 primary 承诺的子集**——standby 里每一行都来自 primary 的一次发送，而 primary 只在确认之后才 ACK。因此：

- 主重启后向备**取回**自己丢失的租约行是**安全**的：取回的东西不可能包含「主从未答应过客户端的绑定」。
- 反之（备向主发送自己的行）不成立，所以**方向是单向的**。

这条推论让 INV-5 有了可执行的形态：恢复时不比「内存条数」也不比「日志行数」，而是比 **primary 已 ACK 的序号集合** 与 **standby 已应用的序号集合**（见决策 4）。

---

## 决策 3：「备持久确认后 ACK」= 备在自己的 `WAL + synchronous=FULL` 库里**提交**该变更后回复序号

**规则**：primary 处理 REQUEST 的 ACK 路径变为：

```
本机写租约（已有，WAL + synchronous=FULL）
  → 把该租约的变更以 (seq, ops) 发给备
  → 等在 confirm_timeout 内收到「已应用到 seq」
  → 收到：发 ACK
  → 没收到：不发 ACK，也不发 NAK
```

**为什么确认必须是「已提交」而不是「已收到」**：备收到报文后崩溃，恢复后它的库里没有这条租约；此时主已 ACK，客户端在使用地址，而备在主故障后接管时会把这个地址再分配出去 —— 真实网络里的地址冲突。

**为什么超时后是静默、不是 NAK**：NAK 是「这个地址不能用」的意思，客户端收到会**放弃当前地址重新开始**。而事实是「我暂时无法做出承诺」——地址本身没问题。静默让客户端按 RFC 2131 重传；重传路径上对端可能已经恢复，客户端拿到的还是同一个地址。**用 NAK 表达「我暂时忙」会把一次可恢复的暂停变成一次不必要的地址变更。**

**超时上界**：`dhcp_ha.confirm_timeout`（默认 `2s`），必须小于客户端的重传间隔量级，否则客户端会在我们还在等确认时就重传，放大负载。

---

## 决策 4：水位来自**序号**，且**心跳超时绝不 promote**

**规则**：

- primary 为每一次复制分配一个**单调递增的 `seq`**（持久化在本机 store 的 meta 里）。`ops` 携带它。
- standby 在提交后记录 `applied_seq`（水位），这是它唯一能证明的事实。
- `GET /ha/v1/status` 交换：`node_id`、`role`、`applied_seq`、`acked_seq`、`uptime`。
- **对端超过 `peer_stale_after` 没有回应，只允许进入 `paused`**（决策 5），**不允许 promote**。

**理由**：这是 INV-4 的直接落地。只有「显式运维动作 + 水位核验」才能在双节点下区分「对端死了」与「我只看得见自己这一半」——而这种区分**不能由心跳做出**，因为两条链路（数据网、心跳网）都不可能保证同时可见。

**明确否决**：自动 promote、基于租约的领导者选举、split-scope 双活（ADR 0001 已否决其 HA 表述）。不引入 etcd/Redis 等外部见证设施（决策 2）。

---

## 决策 5：状态机 —— 四态，且「暂停」是默认的一态

| 状态 | 何时进入 | 能否签发新绑定 / 延长租约 | 对客户端 |
|---|---|---|---|
| `solo` | `dhcp_ha.enabled = false` | 是 | 与本 ADR 之前完全一致 |
| `primary` | 启用 HA，对端在水位内可达 | 是 | ACK |
| `paused` | 启用 HA，对端不可达/未确认，**且未获显式批准** | **否** | **静默**（不 ACK 不 NAK） |
| `primary-degraded` | 启用 HA，对端不可达，**且运维显式批准单副本** | 是 | ACK（并在日志/探针/指标上持续标注） |
| `standby` | `role = standby` | 否（它不是作者） | 不监听 67，不应答 |
| `fenced` | 运维动作，或本节点怀疑自己曾被分区 | **否**，且拒绝应答任何请求 | 静默 |

**`paused` 的含义要写准**：暂停的是**新绑定与租约延长**（INV-6 模式 1 的原话）。**已经持有的租约到期自然失效**，期间客户端续租会得到静默 —— 这不是缺陷，而是「无第二副本时不做出新承诺」的必然结果。它是**默认态**，不是错误态。

**闸门落在 ACK，不落在 OFFER（实现时确认）**：暂停期间 DISCOVER 照常得到 OFFER。理由有两条，缺一不可。其一是判据本身：决策 3 要求确认的是**客户端将要依赖的绑定**，而 OFFER 只是一条带过期的预留，客户端从未被告知可以开始使用地址。其二是代价：不发 OFFER 只会让客户端多一次重传，不换来任何安全性 —— 而客户端拿到 OFFER 却拿不到 ACK 时，它本来就什么都没持有。反过来说，**撤销型操作（RELEASE / DECLINE）在暂停期间照常处理**：忘记一个承诺不会破坏任何不变量，只有创建或延长承诺才会。

**`fenced` 与 `paused` 的区别**：`paused` 是「我还想服务，但第二副本不在」；`fenced` 是「我不确定自己是不是还该服务」——后者更保守，连应答都不发。围栏的解除也必须显式。

---

## 决策 6：降级必须显式，且必须是可观测的

**规则**：

1. 单副本降级**只能**由运维动作产生：`goddi ha degrade --confirm`。它在本机 store 的 meta 里留下标记与时间戳，并写一条审计。
2. **代码里没有任何路径**会自行设置该标记——包括心跳超时、启动自检、重试失败。
3. 对端恢复并追平水位后，该标记**自动清除**（回到 `primary`），因为降级的理由消失了。
4. **启动时必须打印当前冗余状态**（`solo` / `primary` / `paused` / `primary-degraded` / `standby` / `fenced`），`/ready` 的 reasons 与指标同时报告。
5. 单副本降级期间，**配额与探针把它标为 `degraded`**（不是 `failing`）——它仍在服务，但失去了冗余。（`/health` 不受影响：liveness 不看降级，这是 W07-d 已定的规则。）

**理由**：INV-6。静默降级会让系统在运维不知情的情况下失去冗余，故障影响面在**第二次**故障时才暴露。

---

## 决策 7：接管（takeover）是显式动作，且必须过水位核验

**规则**：`goddi ha takeover --confirm` 在 standby 上执行，依次要求：

1. **围栏动作已完成**：运维已确认旧主不可能再写（关机、断网、或已 `fenced`）。命令要求显式传入这一确认，无法用参数绕过。
2. **水位核验**：standby 报告自己的 `ha_applied_seq`，与它记录的对端水位 `ha_peer_seq`（对端曾到达的最高序号）相减得到缺口，并要求运维用 `--accept-gap <n>` 报出**确切数字**。数字不对就拒绝。
3. 接管后本节点**成为新的 primary**，从 `max(applied_seq, peer_seq, 本机 seq) + 1` 继续分配序号；旧主再次出现时必须先被 `fenced` 才允许加入（否则它带着更高的 seq 归来会造成回退）。
4. **安静窗口**：对端水位的时间戳太新（`3 × peer_stale_after` 以内）就**拒绝接管**。这是本 ADR 里**唯一无法用参数绕过**的拒绝。

**为什么第 3 条要写死**：两个 writer 的序号空间若不衔接，备会把手里的旧行当成「比主新」而拒绝应用，或主会接受一批倒退的行。

**缺口意味着什么（这一条要读准，很容易说反）**：缺口里**不可能**包含任何「客户端被告知过」的绑定。ACK 只在备确认后给出（决策 3），而备没应用过的东西，主就没有对客户端承诺过——所以缺口里是那些走**异步**复制的动作（offer / quarantine / release / decline / expire），它们或是有过期的预留，或是本机状态的清理。**危险的方向由决策 3 关掉了**：因为每一条 ACK 过的绑定都已在备的集合里，新主不会发出一个「客户已经在用」的地址。缺口的代价在另一个方向——旧主写下的东西不可撤销地丢了，新主对地址空间的判断与旧主不同（通常表现为池「更满」，即地址被白占）。

**所以它是一个判断，不是一个正确性闸门**：没有任何算式能代替运维回答「丢了这些可不可接受」。要求报出**确切数字**而不是接受一个开关，是因为「接受任意缺口」与「不知道缺口有多大」在运维上无法区分——而 `--accept-gap 7` 会强迫人先读到 7。

**为什么第 4 条要写死，以及它不是什么**：一个在窗口内回过话的主是活的，而两个 writer 是接管存在的唯一要避免的失败。这一条**刻意不冒充分区探测器**——分区的主与死掉的主对备同样沉默，把倍数调多大都改变不了这个事实，所以它只用来拒绝「我还看得见它在说话」这一种情况。**倍数不要照搬到生产**：`3` 是跟着对端链路的重连节奏设的（本版 `peer_stale_after` 默认为秒级），不是从生产流量里标定出来的（见「未验证项」第 2 条）。

## 配置面

`ClusterConfig` 与 DHCP 无关，保持不动。`DHCPHAConfig` **按本 ADR 重定义**（当前它在全仓无任何实现引用，重定义不破坏任何行为）：

```yaml
dhcp_ha:
  enabled: false                 # 默认关闭：不监听任何 HA 端口，单节点行为不变
  node_id: ""                    # 本节点标识；启用时必填，两节点必须不同
  role: "primary"                # primary | standby
  listen_addr: "0.0.0.0:647"     # 本节点监听对端
  peer_address: "10.0.0.2:647"   # 对端地址
  peer_token: ""                 # 共享令牌；经 GODDI_DHCP_HA_PEER_TOKEN 注入，不落库
  confirm_timeout: "2s"          # 等备确认的上界（决策 3）
  heartbeat_interval: "1s"
  peer_stale_after: "5s"         # 只用于进入 paused，绝不用于 promote（决策 4）
```

**校验规则（fail-closed）**：`enabled = true` 而 `node_id` / `peer_address` / `peer_token` 任一为空 → **拒绝启动并点名该设置**。一个「开了 HA 但没有对端」的实例是最坏的形态：它以为有冗余，实际没有，而且没有任何地方会报出来。（同 W10-c 的管理白名单：读不出的名单不能表现成没有名单。）

**不是配置项的两处**：①**安静窗口的倍数**（决策 7 第 4 条的 `3`）是编译期常量 `takeoverQuietMultiple`，刻意不给环境变量——一个能把它调到 0 的旋钮，等于把「两个 writer」变成一个可配置的后果。②**记录的角色**（`ha_role`）是 store 里的事实，不是配置；文件里的 `role` 只在从未发生过 promote/fence 的节点上生效。

## 本 ADR 刻意不做

1. **不引入外部见证**（etcd / Redis / 仲裁节点）。代价如实记录：**双节点无法自动区分宕机与分区，因此永远不会有自动 promote**。这是决策，不是缺口。
2. **不做自动 promote**，包括「主长时间不可达就接管」。见决策 4。
3. **不做 split-scope 双活**。ADR 0001 已否决其「HA」表述：拆池是静态地址空间划分，不提供接管、不保证原 IP 续租。
4. **不内置 VIP / Anycast 控制器**。DNS 侧两个可达地址经 Option6/终端策略下发；是否需要 Anycast 由部署侧决定，产品不代管网络。
5. **不做跨节点的事务复制**。复制的是**租约事实**，粒度是「一条租约的当前行」，不是 SQL 事务重放。
6. **不做 standby 的自动追平外的任何写**。standby 不服务客户端，它唯一的职责是「在主故障后能证明自己知道什么」。

## 未验证项（实现时如实标注）

1. **真实双进程 + 控制库停机下的演练**（INV-3 的进程级形态）需要能同时起两个 DHCP 节点并绑定 `udp4 :67` —— 非特权环境做不到，只能用非特权端口做等价演练，**绑 67 的行为本身不被验证**。
2. **`confirm_timeout` 的取值未经生产流量标定**：2s 是「小于客户端重传量级」的推理值，不是实测值。
3. **序号空间的持久化在「主连续重启 + 备不重启」下的单调性**有单测，但**没有跨真实重启的端到端用例**。
4. **备战接管后的地址冲突概率**未量化：水位核验能证明「哪些 ACK 我可能漏了」，不能证明客户端一定不再使用它。真正的收敛依赖客户端续租时的重新确认。
5. **真实接管演练未做**：W09 的进程级冒烟是在非特权端口上把主 kill 掉、睡过安静窗口、再接管，验证的是角色切换与随之而来的启动路径；**真双机 + 真绑 67 + 客户端在途续租**的接管演练没有做（原因同第 1 条）。

## 实施记录（W08，2026-09-10）

本 ADR 由 **W08** 落地（`internal/dhcp/ha`，配置面在 `internal/config/dhcpha.go`，接线在 `cmd/goddi/main.go`，请求路径闸门在 `internal/dhcp/server`）。纸面上没有穷尽的几处决策一并记在这里，以免下一批把它们当成自由选择：

**1. 谁拨号：standby 拨 primary。** `listen_addr` 是「我在这里接受对端」，但只有一边拨号才不会产生两条互相竞争的连接。选 standby 拨号，因为需要重连的是它：一个重启过的 standby 必须重新建立镜像才有任何用处，而这个方向的恢复不能依赖运维介入。primary 只接受，一次一条连接——**第二个同时到达的镜像会排队而不是被并行服务**：两个镜像共享同一套水位，等于两个节点被信任而只有一个在承重。

**2. 每次重连都发全量快照，不做增量追赶。** primary 唯一能诚实知道的「备已经有什么」就是备确认过的水位，而快照恰好让这个问题不再需要回答。代价是每次重连一次有界传输（本版容量上限 2 万租约，快照量级几 MB，帧上限 32 MiB 设在其上数倍）；换来的是整类「缺口追踪」缺陷的消失——那类缺陷只在生产里暴露。

**3. 确认失败后不回滚本机那一行。** 回滚会让镜像持有本机已删除的行，镜像从此不再描述本机曾处于的任何状态，承重推论当场失效。代价如实记录：**幽灵绑定**——一条客户端从未被告知、却占着池直到租约自然到期的行，其数量与确认超时次数同阶。

**4. 序号在每次分配时持久化。** 计数器的单调性是接管算术的前提（决策 7 第 3 条）；重启后从零开始的计数器会把备已经见过的号再发一遍，而备会把重复读成「已应用」。

**5. 镜像的写不产生审计条目。** W10-b 的审计由 `lease.Manager` 在 Go 侧写，而镜像的 apply 走直连 SQL 绕过管理器。这是刻意的：审计回答的是「谁做了什么」，不是「哪个字节变了」；替另一台机器写审计等于伪造作者。

**6. 镜像的 apply 会在 `dhcp_lease_dirty` 留下痕迹**（dirty 触发器对任何写入都生效），所以每个 apply 事务末尾显式清空该队列，且 standby 的 `PushLeases=false`。否则 standby 会把镜像里的租约向上推送，把别人的绑定报成自己的。

**7. 镜像不是「hold 住的行」，是整表的副本。** 快照与增量都携带全部列、全部状态（含 `expired`/`released`），不做按状态筛选。理由：恢复比对的是**已 ACK 的序号集合**（决策 4），不是行数；而一个「按状态挑选过的子集」在接管时会把手里的死行当成从未存在，进而让镜像的状态与它自称的水位对不上。

**实施中发现并修掉的三个缺陷**（都由「会因撤销而失败」的用例发现，详见 `docs/实施计划-v0.6.0.md` 的 W08 完成记录表）：未在收到帧时刷新对端存活时钟（健康且安静的一对会被自己拆掉）、降级标记的自动清除挂在「水位是否前进」的分支里（`seq=0` 的节点永不前进，一次降级即永久降级）、会话结束的日志写在标记下线之前（同一行里 `state=primary`）。

## 实施记录（W09，2026-09-10）

本 ADR 的**算子面**由 **W09** 落地：机制在 `internal/dhcp/ha/role.go`（`EffectiveRole` / `Operator` / 水位核验 / 接管续号 / 围栏 / 重新加入），运行期采纳在 `internal/dhcp/ha/replicator.go`（`watchOperatorDecisions`），CLI 与接线在 `cmd/goddi/main.go`。纸面上没有穷尽的几处决策一并记在这里：

**1. 算子动作只走 CLI，不做 API。** `degrade` / `takeover` / `fence` / `rejoin` 是**判断**，不是**观测**。一个网络可达 + 令牌被盗的请求，不该能决定这套部署还有没有冗余。CLI 的前提是「能登到这台机器」，这恰好是这些动作本来就要求的信任级别。（`ha status` 同样没做成 API——它读的是本机 store。）

**2. 记录的角色压过配置的角色。** `EffectiveRole` 先读 store 的 `ha_role`，读不到才用文件里的 `role`。理由：文件是**事前的意图声明**，promote/fence 是**事后发生的事实**；让文件赢，就会出现「被围栏的节点下次重启变回 primary」。记录值不被本版认识时**报错**，不回退到配置——回退会把节点带回运维刚刚把它移开的那个角色。

**3. `--confirm` 的闸门写在机制入口，不在 flag 解析器里。** 五个动作（`degrade` / `takeover` / `fence` / `rejoin` 各一个，`takeover` 另需 `--old-primary-cannot-write`）的守卫都在 `Operator` 方法的开头。放在 CLI 层的守卫只保护 CLI；放在方法入口，未来的任何新调用点都没有「忘了加确认」这个选项。

**4. 接管必须同时改角色与授权。** 只写 `ha_role=primary` 而不置降级标记，新主会落回 `paused`（`paused` 就是「没有第二副本」的默认态）→ 接管完仍然不 ACK，整个功能等于没做。因此 promote 在**一个事务**里同时写 `ha_role` 与降级标记。

**5. 接管后续号取三者最大值，且必须清掉 `ha_applied_seq` 与 `ha_acked_seq`。** 续号规则见决策 7 第 3 条（`max(applied, peer, 本机)`）；**清水位是 W09 补的**：残留的 `acked` 高于新 `seq` 时，`Confirm` 的等待会被**瞬时**满足（备的确认「已经到过」那个号了），于是**没有第二副本也会 ACK**——正是决策 3 关掉的那个方向。`rejoin` 同样清 `acked`。

**6. 降级标记只有一个写者，且运行中的服务必须采纳它。** `Operator.Degrade` 是唯一写者；W08 挂在 `Replicator` 上的 `MarkDegraded` **已删除**，避免在服务进程里长出第二个作者。服务通过 `watchOperatorDecisions`（周期 = `heartbeat_interval`）把运维的写入采纳进来——CLI 存在的场景恰恰是「服务不能重启」的那个场景，只改库不通知等于没做。

**7. 降级状态下的 `Confirm` 自己签发承诺。** `!state.Redundant()` 时**立即返回成功**，不等第二副本。等就必然超时（没有副本可等），而超时的语义是「不 ACK」——于是降级标记等于无效。这是 `degraded` 与 `paused` 的分水岭：两者都没有第二副本，差别只在**运维是否授权**。

**8. 降级标记由两个互为镜像的摘除者清除。** `goddi ha degrade --undo`（人）与 `noteConfirmed`（备追平水位，机器）。**这两条不对称，如实记录**：人写的那条留审计（动作名两个方向同为 `dhcp_ha_degrade`，`detail` 里是 `granted…` 还是 `withdrawn…`），机器摘掉时**不写审计**，只记一行日志（`HA: the mirror has caught up; this node is redundant again`）并让 `/ready` 与 `goddi_dhcp_ha_redundant` 变回去。所以审计能回答「降级是什么时候被批准的」，回答不了「它是什么时候消失的」——后者要在日志里按时间点找。

**8b. 算子是谁：`cli:<登录账号>`。** 命令行上没有经过认证的运维身份，唯一存在的行动者是跑这条命令的操作系统账号，审计就照实写它（`user_id = "cli"`、`username = "cli:" + 当前账号`）。这**不是**登录鉴权，只是「能登到这台机器」的那个信任级别的记录——不要把它读成「某个具名管理员批准了」。

**9. `ha status` 如实报 `unknown`，不报最乐观值。** 本命令只带 `-c path`，Go 探不到监听进程，所以「本机此刻有没有第二副本」在只读 store 上**不可判定**。输出里 `redundancy_known: false` / `redundant: unknown from this store`；只有运维亲手写下的两个状态（`degraded` / `fenced`）可以由 store 断言。（**第一版把 `unknown` 报成了 `primary`**——fail-open 的哑对象会让脚本据此认定节点安全，这条是进程级冒烟抓出来的。）

**10. 报告类命令先 `os.Stat`，且不下 PRAGMA。** 打开一个 SQLite 路径本身就会创建文件，而 `journal_mode=wal` 是**永久**改动。一个只读的 `ha status` 不该在宿主机上留下任何东西，因此新增 `dataplane.OpenReadOnly`（先查存在、`mode=ro`、不建目录、不施 PRAGMA、不跑迁移）；冒烟用例断言 **`data_dir` 在 `ha status` 之后仍然不存在**。

**11. `ha_peer_seq_at` 必须亚秒精度。** 它进的是「主最近一次说话距现在多久」的算式，而安静窗口是秒级——RFC3339 的秒截断带来最多 1 秒的量化误差，足以把一个本应被拒绝的接管放行。改用 `time.RFC3339Nano`（读者无需特殊处理，`time.Parse` 兼容）。

**12. 接线不产生 `failing`。** `paused` / `primary-degraded` / `fenced` 一律折成 `degraded`（`/ready` 的 reasons：`dhcp_ha_no_second_copy` / `dhcp_ha_serving_without_a_second_copy` / `dhcp_ha_primary_unreachable` / `dhcp_ha_fenced`）。**只有 `failing` 是 503**，而这三个状态都是「按指示行事」，报 `failing` 会招来重启一个没有任何进程内故障的进程。

**13. 指标在 HA 关闭时缺席，不是 0。** `goddi_dhcp_ha_redundant` / `goddi_dhcp_ha_promising` 只在 `enabled = true` 且本节点不是 standby 时注册——0 读作「这套部署丢了第二副本」，而一台从来没有过副本的机器不该拉响这个警报。两个布尔量对应两个不同的问题（有没有第二副本 / 还愿不愿意承诺），因为把状态名做成 label 会累积序列，而两个问题才是告警真正要问的。
