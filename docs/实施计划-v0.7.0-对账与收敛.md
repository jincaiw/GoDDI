### 3.3 必须保留的边界

- 三进程运行在同一台机器，共用同一个 SQLite 控制库；停止 control 进程本身不会使共享数据库不可写；
- `BEGIN IMMEDIATE` 只模拟写不可用，WAL 下读仍可进行，不等同于真实多主机读分区；
- 脚本直接写租约和 DHCP→DNS 事件，绕过真实 `lease.Manager` / `enqueueDNSEvent`，不等同于真实 DHCP REQUEST/ACK；
- 演练覆盖几十秒级追平，不覆盖长时间积压、真实掉电、relay 或升级迁移。

## 四、B7.2 实施结果（2026-09-12）

### 4.1 首条修订 diff 语义

- `Service.DiffRevisions` 允许 `from=0`，按空对象与目标修订比较，返回全部新增字段；`to` 必须为正数。
- API `GET /api/v1/config/revisions/{id}?with_changes=true` 不再把首条修订误报为空变更，和 `PublishResult.Changes` 语义一致。
- 现有 `TestPublish_FirstRevisionIsNumberedOne`、新增首条 diff 测试及 API 回归共同钉住该契约。

### 4.2 修订保留与清理

新增 `Service.PruneRevisions(resource_type, resource_id, keep)`，当前采用显式维护调用而非隐式后台删除：

- `keep >= 1`，仅清理指定资源的旧 `applied` 修订；`staged` / `failed` 证据不自动删除；
- 保留最新 `keep` 条修订；即使超出窗口，最后一条 `applied` 仍保留；
- 被 `config_release_outbox.revision_id` 引用的修订不删除；
- 删除在单个事务内完成并返回删除行数，便于后续接入 CLI、定时维护或审计日志；
- 当前未实现多节点发布协调，B7.2 的已完成范围是单节点配置治理与可审计清理边界，R-01 继续保留。

验证：

- `go test ./internal/configver ./internal/api/handler`：通过；
- 覆盖首条 diff、keep 窗口、最后 applied、outbox 引用保护、非法 keep/type。

## 五、B7.5 实施结果（2026-09-12）

### 5.1 真实二进制与恢复矩阵

- 从历史 `v0.5.2` tag 构建旧二进制 `/tmp/goddi-b75/goddi-old`，当前工作树构建新二进制 `/tmp/goddi-b75/goddi-new`；版本输出分别为 `0.5.2` 与 `0.6.0`。
- 新二进制迁移空源库成功，control schema 到 25；使用相同 JWT / encryption 测试密钥创建加密快照 `/tmp/goddi-b75/drill/new-snapshot.goddi-snap`。
- 新二进制将该新快照恢复到空目标成功，恢复前闸门报告“本二进制可以读取该归档”，control 文件成功替换。
- 旧二进制的命令面只有 `migrate/serve/unlock` 等旧命令，没有 `backup/restore`，也没有迁移 `--check` 或恢复闸门；因此不能把“旧二进制拒绝新归档”伪造为已执行的旧 CLI 证据。旧二进制读取新 schema 文件后，旧迁移器未降级 schema，但它本身没有 fail-closed 的前置闸门，说明 R-06 的关键保护来自 `0.6.0` 新闸门，而不是旧版本兼容性。
- 用旧迁移集合创建 schema 15 的旧库快照（临时 Go harness 仅打包 `control`，明文仅用于无密钥旧 schema 夹具），新二进制恢复到空目标成功，报告 schema 15 落后于本二进制最高 25；随后 `goddi migrate` 应用 016–025，control 达到 schema 25。
- 新二进制升级后的 `migrate --status` 报告 control `25 / 25，无待应用`；dnsdata/leases 因旧夹具未创建而各有 5 条待应用，属于快照中明确 absent 的可选数据面，不是 control 升级失败。

### 5.2 B7.5 结论与边界

B7.5 的真实证据闭合范围是：当前二进制对同版加密快照可恢复；旧 schema 快照可被当前二进制接受并迁移到当前 ceiling；新二进制在恢复写入前执行 migration ceiling 与产品版本关系判断。旧 `v0.5.2` 二进制没有恢复子命令和前置闸门，故不能声称完成“旧二进制主动拒绝新归档”对称测试；该能力需在未来仍保留 restore CLI 的相邻版本上补测。未验证真实掉电、跨主机文件传输损坏、密钥丢失和数据面数据库均已存在的完整升级场景。

## 六、B8 发布后实施计划（基线：v0.7.0）

### 6.1 目标与退出标准

B8 不把“企业级 DDI”作为一次仓内重构完成，而是按“先补可验证协议与过载边界，再准备外部验收，最后单独设计架构级能力”的顺序推进。B8 的退出标准是：仓内可闭合项有代码、负向测试、契约/文档守卫和完整门禁；外部项有明确拓扑、输入、操作步骤、判据和证据归档位置；任何单机模拟、代码存在或示例配置均不得写成 GA 证据。

### 6.2 当前已完成能力（不重复实施）

- 单节点配置 revision、首条 diff、rollback、release outbox 与显式 revision pruning；
- DHCP REQUEST 三态分类、server-id 处理、DECLINE quarantine、分配前冲突探测、报文级 panic recover；
- DHCP HA 的备确认后 ACK、围栏、接管/重入状态机和 `/ready` 接线；
- DHCP→DNS durable outbox、DNS 本地副本和进程级追平演练；
- IPAM linkage 进程内接线、IPAM 双连接并发唯一性测试；
- backup/restore、schema ceiling 与旧 schema 前移证据；
- 二级区周期同步已接入运行时；DNSSEC、Prometheus、TLS 默认状态和容量边界已如实声明；
- v0.7.0 已发布，不能通过重写历史计划或新增同值 tag 改变上述发布事实。
