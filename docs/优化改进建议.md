# GoDDI 优化改进建议

> 依据：《上线前测试报告》（v0.1.11 候选）
> 排序沿用既定技术优先级：**可靠性 > 缓存 > 上游质量 > 配置正确性 > 日志与监控 > 极限 QPS**
> 工作量标记：S（半天内）/ M（1–2 天）/ L（3 天以上）

---

## 总览

| 优先级 | 数量 | 含义 |
| --- | --- | --- |
| P0 | 3 | 发布前必须处理，否则存在"功能假象"或可用性事故风险 |
| P1 | 8 | v0.1.12 内完成，直接影响稳定性与安全边界 |
| P2 | 9 | v0.2.0 规划，属质量与能力增强 |

## 一、可靠性（Reliability）

### R1 · DNSSEC 是空实现 —— **P0 / M**

- **现状**：`internal/dns/dnssec/dnssec.go:240-276` 的 `SignZone` 只校验 ZSK/KSK 存在，然后把 `dns_zones.dnssec_enabled` 置 1 并 reload，**不生成任何 RRSIG/DNSKEY 记录**。
- **风险**：控制台显示"已启用 DNSSEC"，但权威应答里没有签名。下游校验方会判定为 Bogus，属于静默故障，比"不支持"更糟。
- **建议**（二选一）：
  1. **短期（推荐）**：在 UI 把 DNSSEC 开关标注为"实验功能（尚未生成签名）"，`SignZone` 返回明确提示，或在配置里增加 `dns.dnssec_enabled` 总开关默认关闭；
  2. **中期**：补齐真实签名链路——生成 `DNSKEY`/`RRSIG`/`NSEC`（或 NSEC3）并在应答中携带，配套密钥轮转与 `CDS`/`CDNSKEY` 发布。
- **收益**：消除"假成功"；为后续真签名留出清晰路径。
- **工作量**：方案 1 为 S，方案 2 为 L。

### R2 · 登录锁定 15 分钟且无解锁入口 —— **P0 / S**

- **现状**：`internal/auth/rate_limiter.go:35-36` 默认锁定时长 15 分钟，计数与锁定时间持久化在 `login_rate_limits` 表；除直接改库外没有解锁手段。
- **风险**：任何人只要知道管理员用户名，就能用错误密码把管理员锁在门外，形成低成本 DoS。
- **建议**：
  1. 配置化锁定时长（`security.login_rate_window_seconds` 已存在但默认 0 → 15 分钟，建议默认收敛到 5 分钟并在文档说明）；
  2. 提供解锁入口：管理员可通过已登录会话调用 `POST /api/v1/auth/unlock`，或提供 `goddi unlock --user <name>` 子命令；
  3. 锁定触发时输出 WARN 日志（含来源 IP），便于溯源。
- **收益**：把"可被武器化的保护机制"变成可控策略。
- **工作量**：**S**。

### R3 · SQLite 单连接导致全局串行 —— **P1 / M**

- **现状**：`internal/database/database.go:47-57` 对 sqlite 设置 `SetMaxOpenConns(1)`。已启用 WAL 与 `busy_timeout=5000`，但**所有读写共用一条连接**，备份/恢复这类长事务会整体阻塞 API（本轮已修掉由此引发的一处 DNSSEC 死锁，根因仍在）。
- **建议**（渐进三步）：
  1. **先摘掉长事务**：备份导出改为"快照到临时文件 → 异步落盘"，恢复改为分批提交（每 500 条一个事务），避免单次事务持连接过久；
  2. **读写分离**：维护两个 `*sql.DB`，`writer`（MaxOpenConns=1）+ `reader`（MaxOpenConns=8，只读查询走 reader）。WAL 下读不阻塞写，可立即获得并发收益；
  3. **补充 PRAGMA**：`synchronous=NORMAL`（WAL 下的标准取舍）、`busy_timeout` 提升到 10s，并加连接池等待指标。
- **收益**：消除长事务导致的全站卡顿，API 并发显著提升。
- **工作量**：第 1 步 **S**，第 2 步 **M**。

### R4 · DHCP 收包循环无 panic 恢复 —— **P1 / S**

- **现状**：`internal/dhcp/server/server.go:166-201` 的 `receiveLoop` 每接口单 goroutine 串行处理，整条循环没有 `recover()`；`handleMessage` 中任何 panic 都会静默终结该接口的 DHCP 服务。
- **建议**：
  1. 在 `handleMessage` 外加 `defer recover()`，记录堆栈后继续循环（与 DNS 侧 `ServeDNS` 已有的防护对齐）；
  2. 增加 `deferred ACK`（或限流丢弃）机制：处理前先判定队列/速率水位，超出则丢弃而非阻塞；
  3. 暴露 `dhcp_packets_dropped_total` 指标。
- **收益**：单个异常报文不再导致 DHCP 整体不可用。
- **工作量**：**S**。

### R5 · 后台 goroutine 生命周期与 `metrics.Shutdown()` —— **P2 / S**

- **现状**：`internal/metrics/metrics.go:177` 的 `Shutdown()` 在全仓库无调用点；`StartPeriodicSync` 等后台任务同样未被编排。
- **建议**：在 `main.go` 的优雅退出路径统一注册 shutdown 钩子（query logger → metrics → task manager → DNS/DHCP server），确保缓冲指标与查询日志落盘。
- **收益**：重启不丢尾部指标与日志，便于事后分析。
- **工作量**：**S**。

## 二、缓存（Cache）

### C1 · `Get` 走全局独占锁 —— **P1 / M**

- **现状**：`internal/dns/cache/cache.go:175-178`，`Get` 使用 `c.mu.Lock()`（写锁）。原因是命中后要 `LRU.MoveToFront` 修改链表。当前 64 并发下仍有 38k QPS，说明尚未成为瓶颈，但**锁竞争会随核数线性恶化**。
- **建议**：
  1. **分片**：按 `cacheKey` 哈希分 32 片，每片独立 `RWMutex` 与 LRU，锁竞争降为 1/32；
  2. 或**惰性提升**：命中只累加 `atomic` 计数与时间戳，由后台 goroutine 定期批量重排 LRU。
- **收益**：多核环境下读路径近线性扩展，为后续万兆/多核部署留余量。
- **工作量**：方案 1 **M**。

### C2 · `PopularEntries` O(n²) —— **P2 / S**

- **现状**：`internal/dns/cache/cache.go:590-600` 每次调用都全量遍历 `c.entries` 再排序，且持有读锁。
- **建议**：维护一个 Top-N 小顶堆（N=100），命中时 O(log N) 更新；或把结果按 10s 缓存，避免每次 API 请求重算。
- **收益**：大缓存（1 万条以上）下 `/dns/cache` 页面不再卡顿。
- **工作量**：**S**。

### C3 · 缺少内存上限与命中率告警 —— **P2 / S**

- **现状**：`max_entries` 限制了条数，但没有字节级上限；`hit_rate`/`miss_rate` 已在 `/metrics` 暴露。
- **建议**：补充 `cache_entries`、`cache_evictions_total`、`cache_memory_bytes` 指标，并对"命中率 < 60% 持续 10 分钟"配置告警规则示例。
- **收益**：缓存异常（如 TTL 配置错误导致命中率崩塌）可被主动发现。
- **工作量**：**S**。

## 三、上游质量（Upstream）

### U1 · 每次转发都新建 `dns.Client` 与套接字 —— **P1 / M**

- **现状**：`internal/dns/forwarder/forwarder.go:420/461/507`，每次上游查询都构造新的 `dns.Client` 并由 `Exchange` 重新 dial，高并发下 fd 与临时端口压力大、延迟抖动明显。
- **建议**：
  1. 为每个 upstream 预建并复用 UDP/TCP 两个 `dns.Client`（避免重复分配与超时计算）；
  2. 开启 `dns.Client.SingleInflight`（miekg 提供），合并并发的相同查询，直接消解缓存击穿风暴；
  3. 进一步可做 UDP `dns.Conn` 池（每 upstream 保持 4–8 条，用 `ExchangeWithConn` 复用）。
- **收益**：降低 fd/端口占用与 P99 抖动，缓存未命中时的放大流量明显收敛。
- **工作量**：第 1+2 步 **S**，第 3 步 **M**。

### U2 · 上游地址未做私网过滤 —— **P1 / S**

- **现状**：转发器与调试查询可把 `127.0.0.1`、`10.0.0.0/8`、`169.254.169.254`（云元数据）等配置为上游。
- **建议**：复用本轮为拦截列表引入的 `filter.AssertPublicURL` 思路，新增 `netutil.AssertPublicAddr`，在创建/更新转发器与调试查询接口统一校验（允许配置显式开关 `security.allow_private_upstream` 以兼容内网递归场景）。
- **收益**：堵住剩余一处 SSRF 面，同时保留内网部署的可控出口。
- **工作量**：**S**。

### U3 · 上游健康判定与熔断 —— **P2 / M**

- **现状**：有 `SetHealthy`/`recordFailure`，但缺少连续失败阈值、半开探测与熔断状态暴露。
- **建议**：增加"连续 N 次失败 → 熔断 T 秒 → 半开放单个探测"状态机，并把 `upstream_healthy`、`upstream_rtt_ms`（P50/P99）、`upstream_failures_total` 纳入 `/metrics`。
- **收益**：单上游故障时可观测、可自愈，不再依赖人工切换。
- **工作量**：**M**。

## 四、配置正确性

### G1 · HTTP 管理面无 TLS —— **P0 / M**

- **现状**：DNS 侧 DoT/DoH/DoQ 已支持 `cert_file`/`key_file`，但**HTTP 管理面与 API 完全没有 TLS 选项**，`config.yaml` 只有 `server.http_addr: ":6080"`。
- **风险**：管理员密码、JWT、API Token 全部明文传输；配合"CSRF 令牌未绑定会话"，内网嗅探即可接管。
- **建议**：
  1. 增加 `server.tls` 配置段（`enabled`/`cert_file`/`key_file`/`min_version`），启用后走 `ListenAndServeTLS`；
  2. 启用 TLS 时自动下发 `Strict-Transport-Security`、`Secure` + `HttpOnly` + `SameSite=Strict` 的会话 Cookie；
  3. 文档给出"前置反向代理终止 TLS"的推荐部署形态与示例。
- **收益**：满足生产环境最基本的传输安全要求。
- **工作量**：**M**。

### G2 · CSRF 令牌未绑定会话 —— **P1 / S**

- **现状**：`internal/api/middleware/middleware.go:375-405`，令牌为 `timestamp:HMAC(key, timestamp)`，**与用户/会话无关**，任意登录用户签发的令牌可被其他人使用。
- **建议**：把 `session_id` 或 `user_id` 纳入 HMAC 输入（`HMAC(key, sessionID + ":" + timestamp)`），校验时从 JWT 上下文取出同一标识比对。前端无需改动。
- **收益**：CSRF 令牌从"全局有效"收敛为"会话绑定"。
- **工作量**：**S**。

### G3 · `/api/v1/openapi.json` 免认证 —— **P2 / S**

- **现状**：`internal/api/router.go:67` 公开，暴露完整路由清单。
- **建议**：纳入认证（与 `/metrics` 一致），或在配置里加 `api.expose_openapi`（默认关闭）。
- **收益**：减少接口面侦察信息。
- **工作量**：**S**。

### G4 · 部署前置条件未在文档明示 —— **P2 / S**

- **现状**：`docker-compose.yml` 强依赖 `.env` 提供 `GODDI_SECURITY_JWT_SECRET`，缺失时直接报错退出。这是安全正设计，但 README 未突出。
- **建议**：在 README 与 `config.yaml` 注释里补充"首次部署必做清单"：生成 JWT 密钥、配置 `encryption_key`、执行 `/auth/init`、修改默认管理员密码、开启 TLS。
- **收益**：降低首次部署踩坑率。
- **工作量**：**S**。

## 五、日志与监控

### L1 · 高 QPS 下查询日志丢弃不可见 —— **P2 / S**

- **现状**：`internal/dns/querylog.go:65-78` 采用非阻塞队列，通道满即丢弃（设计正确，绝不阻塞 DNS）。压测 39k QPS 时绝大多数条目会被丢弃，但 `DroppedCount()` 未接入 `/metrics`。
- **建议**：
  1. 把 `query_log_dropped_total`、`query_log_written_total` 接入指标；
  2. 增加 `log.query_sample_rate`（如 0.01），高负载时按采样记录而非全量丢弃；
  3. 审计日志同理，补充丢弃计数。
- **收益**："日志为什么少了一半"变成可解释、可调优，而不是黑盒。
- **工作量**：**S**。

### L2 · 静态检查未纳入 CI —— **P1 / S**

- **现状**：CI 只有 `go vet` 与 `go test -race`，`golangci-lint` 本地与 CI 均未安装；`.golangci.yml` 已配置但未生效。
- **建议**：CI 增加 `golangci-lint run` 与 `govulncheck` 步骤，并固定版本。
- **收益**：把本轮靠人工审计才发现的问题（错误分支、并发误用）变成流水线自动拦截。
- **工作量**：**S**。

### L3 · CI 未覆盖 DNS 运行时 —— **P1 / M**

- **现状**：`.github/workflows/ci.yml` 设置 `GODDI_DNS_ENABLED=false`，DNS 核心完全不在 CI 回归范围内。本轮发现的 FQDN 双拼接、通配符匹配、NODATA/NXDOMAIN 等问题都只能靠人工 dig 验证。
- **建议**：在 CI 中启用 DNS（`127.0.0.1:15353`），新增一组 Go 集成测试：建区 → 加记录 → `dig` 校验 → 通配符 → 转发 → 缓存命中 → 删除，断言应答码与记录内容。
- **收益**：DNS 核心改动有自动回归网。
- **工作量**：**M**。

### L4 · 缺少告警基线 —— **P2 / S**

- **建议**：随发布提供一份 Prometheus 告警规则示例（服务不可用、DNS 成功率 < 99%、上游全失败、缓存命中率异常、登录失败激增、备份失败、磁盘水位）。
- **收益**：从"能监控"升级为"能值守"。
- **工作量**：**S**。

## 六、极限 QPS

### Q1 · 压测常态化 —— **P1 / S**

- **建议**：把本轮使用的 UDP 压测脚本纳入仓库（`scripts/bench/`），在 README 记录基准口径（权威区、随机名、并发 16/64/128），每次发布前跑一遍并附上结果。
- **当前基线**（供后续对比）：单线程缓存命中 29,394 QPS / 0.03 ms；随机名 64 并发 38,102 QPS / 1.67 ms；128 并发 36,059 QPS / 3.53 ms；成功率均 100%。
- **收益**：性能回归可被量化发现。
- **工作量**：**S**。

### Q2 · 缓存分片 + 上游连接复用 —— 见 C1 / U1

这两项是继续抬升 QPS 天花板的主要杠杆，建议与 C1、U1 合并排期。

## 七、测试体系

### T1 · 覆盖率提升路线（当前 13.3%，建议目标 40%）—— **P1 / L**

| 优先级 | 模块 | 当前 | 建议目标 | 重点用例 |
| --- | --- | --- | --- | --- |
| 1 | `dns/zone` | 2.3% | 50% | 名称归一化、通配符匹配、NODATA vs NXDOMAIN、FQDN 输入 |
| 2 | `dns/server` | 9.4% | 40% | NOTIFY/IXFR/AXFR 分支、TSIG 校验、限流 |
| 3 | `dns/transfer` | 4.7% | 40% | 区域传送完整性、序列化边界 |
| 4 | `dhcp/server` | 3.1% | 35% | DISCOVER/OFFER/REQUEST/ACK 全流程、异常报文不中断 |
| 5 | `metrics` | 6.8% | 40% | 桶上限溢出到 `(other)`、指标语义 |
| 6 | `dnssec` / `dynamic_update` / `ipam` | 0% | 25% | 至少覆盖入口参数与错误分支 |

### T2 · 补齐本轮修复的回归用例 —— **P1 / S**

建议为本轮 7 项修复各补 1–2 条断言，防止回退：域名/记录名校验表驱动用例、备份不存在返回 404、拦截列表 SSRF 拒绝、登录限速触发与解锁、`InternalErrorWithLog` 不回显内部错误、`/metrics` 401。

### T3 · 补充"故障注入"类测试 —— **P2 / M**

DNS 与 DHCP 处理路径注入 panic，断言服务不退出、请求数不归零；SQLite 长事务并发断言 API 不被无限阻塞。

## 附：若只做三件事

1. **把 DNSSEC 入口标注为实验功能**（R1）—— 避免用户拿到"看起来安全、实际未签名"的错误预期。
2. **给 HTTP 管理面加 TLS**（G1）—— 当前管理员凭据与令牌全程明文。
3. **给登录锁定加解锁入口**（R2）—— 把防护机制从"可被武器化"改回"可控策略"。
