# GoDDI v0.9.0 实施计划：企业级方案复核与生产收敛

> 状态：**v0.8.5 已发布；下一批 N5/N6 仓内收敛计划待用户确认，确认后实施；N7/N8 继续处于验收准备阶段**。
> 基线：已发布 `v0.8.5` / `7e8d39b` / tag `v0.8.5`；`origin/main` 与该提交一致。
> 依据：外部《企业级 DDI 产品评估与实施方案》原始基线为 v0.5.2；本计划已按 v0.8.4 的代码、测试、文档和发布事实重新对账。
> 原则：只按代码和可复核证据标记能力；原型不冒充 GA；单机演练不冒充多主机 HA；外部验收项不以仓内测试替代。

## 一、复核结论

### 1.1 外部方案已过时的判断

外部方案基于 `main@d5b5fe3` / v0.5.2，其中以下结论已经被后续版本改变，不能继续作为当前缺口直接执行：

| 原方案判断 | v0.8.4 复核结论 | 当前分类 |
|---|---|---|
| DHCP REQUEST 状态机、DECLINE、OFFER 语义、收包保护缺失 | 已补齐对应仓内边界和负向测试；Option 82/relay allowlist 也已有仓内实现 | implemented；真实 relay 仍 external-validation-required |
| DHCP HA 完全为空 | 已有 DHCP lease HA 的 primary/standby、sequence、watermark、fence、takeover/rejoin 和 durable apply 契约 | experimental/incomplete；真实多主机 HA 仍 external-validation-required |
| `/ready` 不存在 | `/ready` 已实现并有 readiness 分级、日志变化和演练证据 | implemented；现场告警联动仍 external-validation-required |
| 配置版本、diff、rollback 全部缺失 | 已有 revision、expected revision、idempotency、release outbox、rollback-as-new-revision、首条 diff 和显式 pruning | implemented；多节点发布协调未实现 |
| DHCP-DNS 联动完全没有 | DHCP-DNS durable outbox、generation、consumer、retry/reconciliation 和真实 UDP 查询证据已存在 | implemented with bounded scope；不等同统一 DHCP-DNS-IPAM 事实链 |
| IPAM 完全不能并发分配 | 已有双连接并发唯一性和 WAL/FULL 前提测试 | implemented with evidence boundary；非目标硬件容量证明 |
| DNS 热路径与 DHCP 全部直接依赖 DB | DNS 热路径已内存化；DHCP 默认热路径仍为 SQLite-backed `lease.Manager` | DNS implemented；DHCP migration incomplete |
| WAL/内存 LeaseStore 已可直接切换生产 | 当前仅有分阶段契约、WAL 文件、恢复、AsyncApplier、durable gate、MemoryWriteBridge | experimental/incomplete |

### 1.2 当前仍未闭合的企业级差距

本轮确认四条主线仍未完成：

1. **默认 DHCP 热路径生产迁移**：默认构造仍为 SQLite，`ClaimAvailable` 未进入 `LeaseStore` / `HandleDiscover`。
2. **WAL durable ACK 正式接管**：WAL gate 是可选 hook，未完成统一 mutation、projection watermark、重启 replay、关闭和管理面旁路收敛。
3. **DHCP-DNS-IPAM 统一事实链**：统一 Envelope、迁移期 durable IPAM observation outbox、shared watermark 和 opt-in consumer 已具备最小实现；但 DHCP mutation 尚未真实写入，统一 sequence 分配、DNS consumer 迁移、默认进程装配、完整 lag/gap 观测和跨重启生产 replay 尚未闭合。
4. **生产级多节点配置协调及外部验收**：当前只有协议模型和 501 边界；真实 transport、leader/quorum/fencing、跨主机分区、掉电、relay、容量和长稳未闭合。

本轮 N6 观测收敛新增了 opt-in 状态快照：FactsConsumer 同时报告生命周期、持久化 applied watermark、next expected sequence、durable head、pending/failed backlog、lag 和 gap；failed 事件继续保留在 outbox，不把未知或缺口伪装成健康。该快照未接入默认 DHCP、默认进程或 `/ready`，因此不能据此宣称统一事实链已生产化。

**DHCP 利用率采样健康信号（2026-09-14）**：为 authoritative lease store 的只读利用率 provider 增加 `goddi_dhcp_scope_utilization_scrape_error` 与 `goddi_dhcp_scope_utilization_last_success_timestamp_seconds`。最近一次读取失败置 error gauge 为 1、保留既有 scope utilization 值并继续采样其他 provider；成功采样清除 error、更新时间戳，成功空结果仍清理已消失 scope；首次成功前时间戳序列缺席，错误原文不进入 label。新增 exposition 与 provider 隔离测试，并在告警文件加入采样失败和超过 15 分钟未成功采样告警。该改动仅补齐只读观测，不改变默认 DHCP SQLite 热路径、ACK、DNS 或 IPAM 事实链边界。

## 二、能力分层台账

### 2.1 implemented：不重复实施

- DNS 权威、递归转发、缓存、过滤、DoT/DoH/DoQ listener 配置。
- DHCP 基础报文流程、REQUEST 分类、OFFER/DECLINE/RELEASE 语义、Option 82 parser 和 allowlist。
- DHCP 入口有界队列、固定 worker、过载 fail-closed 和指标。
- DHCP lease HA 的仓内协议边界、fence、takeover/rejoin 和 `/ready` 接线。
- DHCP-DNS durable outbox、generation、retry/reconciliation 和进程级追平演练。
- 配置 revision、首条 diff、发布 outbox、rollback-as-new-revision、显式 pruning。
- backup/restore、schema ceiling、旧 schema 前移和恢复前闸门。
- `MemoryIndex` 的索引、原子内存 `ClaimAvailable`、`ReplaceChecked` 和 WAL 恢复 fail-closed。
- CI、OpenAPI/501 契约、能力声明守卫和 v0.8.4 发布门禁。

### 2.2 experimental/incomplete：本计划继续收敛

- 内存 LeaseStore 仅完成迁移契约，未成为默认事实源。
- WAL durable gate、AsyncApplier、MemoryWriteBridge 尚未组成完整生产事务边界。
- DHCP-DNS-IPAM 之间仍是多个局部事实源和 best-effort observer/outbox。
- 多节点配置发布只有 ADR 和协议模型，没有生产 transport/持久化状态/选主执行器。
- DNSSEC 仍未形成完整 RRSIG/DNSKEY/NSEC/NSEC3 签名链。

### 2.3 reserved/501：保持不误报

- 通用多节点 cluster 管理 API。
- SSO、Apps runtime、管理面 DHCP HA 扩展。
- `internal/cluster.ErrNotImplemented` 不得因协议模型存在而移除。

### 2.4 external-validation-required：仓内不标记通过

- 真实 DHCP relay/Option 82 设备互操作和真实客户端 ACK。
- 跨主机 DHCP HA、网络分区、脑裂和恢复。
- 真实掉电与文件系统/磁盘损坏恢复。
- Prometheus/Alertmanager 实际 scrape、告警触发和恢复。
- 企业 CA 生命周期、DNSSEC validator、真实 DoT/DoH/DoQ 客户端握手。
- 目标硬件容量、峰值冲击、长稳 soak、第三方安全测试。

## 三、拟实施批次

> 以下批次描述实施顺序和退出标准；用户已确认，当前按 N5 → N6 → N7/N8 推进。
### N5：默认 DHCP 生产迁移前置收敛（P0）

**本轮进展（2026-09-13）**：已补齐 WAL durable append 返回 canonical sequence event 的契约；`MemoryWriteBridge` 现在只向异步 projection 提交同一带 sequence 事件，并有临时 WAL 集成测试。新增 `MutationContract` / `MutationCommand`，统一描述 DISCOVER offer、REQUEST activate/renew、RELEASE、DECLINE、EXPIRE 的状态转换、WAL upsert 映射、DNS/IPAM side-effect 和 replay 规则；WAL 事件携带可选 mutation kind 并对未知 kind fail-closed。默认 DHCP 仍为 SQLite，尚未接入生产装配。

**目标**：把现有 WAL/MemoryIndex 原型补成可被生产装配评审的完整契约，但暂不直接切换默认路径。

#### 工作项

1. 定义统一 lease mutation command：覆盖 DISCOVER offer、REQUEST activate/renew、RELEASE、DECLINE、EXPIRE。
2. 让 durable append 返回完整带 sequence 的 `WALEvent`，并保证事件交给 AsyncApplier 的内容与 WAL 内容一致。
3. 明确 memory state、WAL durable、SQLite projection、DNS outbox、IPAM observation 的事务边界。
4. 增加 durable `applied_seq` / projection watermark，并定义 queue full、apply error、gap、replay lag 的 readiness 语义。本轮已新增 `lease_projection_watermark` 表、连续水位推进 API、`ApplyWALEventTx` 投影事务桥和 `NewSQLiteProjectionApplier` 装配辅助，覆盖重复/gap/回滚/异步 apply 测试；该桥可将租约 upsert/remove 与水位放在同一 SQL 事务中，但尚未接入默认 WAL 启动恢复，也尚未把 DNS/IPAM 纳入同一事务。
5. 建立启动顺序：关闭 DHCP → 读取 durable baseline → replay WAL → 校验 pool/reservation snapshot → MarkReady → 开放 DHCP。本轮新增 `RecoverSQLiteProjection`、`StartupCoordinator`、DHCP `StartupGate` 与 `StartupStatus` 观测：按持久化 `applied_seq` 重放未应用 WAL，只有恢复成功才进入 `ready`；配置 gate 后 `Server.Start` 在绑定 DHCP socket 前执行恢复，状态可报告 `state/ready/last_seq/error`，gap/corruption/apply failure 或取消均保持未就绪。现已将有限恢复状态接入 DHCP readiness detail 和现有 data-plane metrics：认证详情仅暴露 `configured/ready/state/last_seq`，失败映射为稳定 reason，Prometheus 仅发布低基数状态、ready、last_seq，不发布错误原文；匿名 `/ready` 仍只返回粗粒度 `status`。默认构造仍不配置 gate，尚未接入全局进程启动。
6. 补齐 shutdown drain/replay 语义，禁止默认 ACK 在 durable event 未落盘时返回。
7. 审计管理 API、metrics、backup、expire sweep 等旁路，避免绕过 authoritative store。本轮变更事务审计结论：`HandleDiscover` 的 OFFER、`HandleRequest` 的 CREATE/ACTIVATE/RENEW、`HandleRelease`、`HandleDecline`、`sweepExpiredLeases` 均仍直接调用 SQLite `lease.Manager`；`MutationContract` 目前只提供校验/事件模型，尚未接入这些调用点。REQUEST 的本地 lease 写入、HA confirm、可选 WAL gate、DNS outbox、IPAM observer 仍是分段顺序；DNS/IPAM 失败不撤销 ACK，lease 与 DNS outbox 也不在同一 SQL 事务。RELEASE/DECLINE/EXPIRE 无 durable WAL gate，管理 API 的删除、过期清扫和统计仍需继续以 authoritative store 旁路审计。该结论保持 `experimental/incomplete`，不把契约存在误报为生产统一事务。

**DHCP → 统一事实链接入审计（2026-09-14）**：`ActivateLease`、`ReleaseLease` 等路径可以取得足够的 Before/After 快照；`ReserveAddress` 只代表 OFFER，不直接产生 IPAM observation；`RenewLease` 当前主要返回 After；`Release/Expire` 的现有 observer 调用存在使用旧快照的边界。`ObservationOutbox` 的 sequence 不能通过 `MAX+1` 分配，后续必须使用同一 SQLite transaction 内的专用单行计数器原子递增，并再调用 `EnqueueTx`；WAL sequence 与 facts projection sequence 不得混用。当前 `Manager`/`LeaseStore` 不接收 `*sql.Tx`，`ExpireLeases` 自持事务并在提交后回调，因此 mutation、DNS outbox、IPAM observation 仍无法直接纳入同一生产事务。最小安全下一步是保持默认 `New` 和 SQLite 权威路径不变，新增显式 opt-in 的 transaction seam，先验证 `Activate/Release` 的完整 Before/After、sequence 分配、outbox 回滚和旧 observer 兼容性，再考虑 Renew/Expire；未完成前不得标记统一事实链为 `implemented`。

**存储归属审计（2026-09-14）**：默认 `role=all` 使用控制库、DNS 库和 lease 数据面库；`dhcp_leases`、DHCP scope、兼容 DNS outbox 与 unified facts producer 均应位于 lease 数据面，而 IPAM projection 位于控制库。新增 `internal/dataplane/migrations/008_facts_storage_placement.sql`，以 `facts_storage_placement` 记录迁移期契约：`producer_store=leases`、`consumer_store=control`、`atomicity=per_store_only`、`status=opt_in`；新增测试证明该契约只存在于 dataplane migration，不会由控制库迁移自动创建。该契约明确不把两个 SQLite 文件伪装成跨库原子事务：未来 producer 事务只保证 lease mutation + facts outbox 在 lease 库内原子提交，consumer 在控制库内原子完成 IPAM projection + watermark + outbox done；跨库一致性仍依赖 durable replay/reconciliation，未完成默认装配前不得标记 `implemented`。

**scope → space 身份契约（2026-09-14）**：新增 `ipam.ScopeIdentityResolver` 作为 producer 侧显式解析 seam，要求在 lease mutation 事务开始前，根据 `scope_id` 和目标 IP 解析稳定的 `space_id/subnet_id`。解析顺序为 DHCP scope 的 canonical CIDR 精确匹配，失败后按包含目标 IP 的最长前缀匹配；缺少 scope、非法 IP、scope 不存在或没有任何包含 subnet 时 fail-closed。该 resolver 只读取 IPAM/控制库，不跨库参与 lease transaction，也未接入默认 DHCP handler；因此它解决的是身份解析契约，不代表跨库原子性或统一事实链已生产化。

**unknown-address DECLINE 契约（2026-09-14）**：新增 `lease.DeclineTombstoneFact` 与 `DeclineTombstoneEnvelope`，为此前没有 authoritative lease 的 DECLINE/quarantine tombstone 提供独立统一 facts payload。事件保留新建 conflict tombstone 的稳定 lease ID，并明确 `tombstone=true`、`action=decline`、`generation=0`；缺少 event/source/space、scope/IP/MAC、错误状态或非零 generation 时 fail-closed。该适配器只构造并校验 Envelope，不写 lease、不写 outbox，未接入默认 `QuarantineIP`/`HandleDecline`，因此不能视为 unknown DECLINE 已进入统一事实链。

**批量 EXPIRE 契约（2026-09-14）**：新增显式 opt-in `FactsMutationWriter.ExpireFactsBatch`，保留现有批量清扫的“事务内选择候选 + 批量更新 + 精确 swept 快照”边界，在同一 lease 数据面事务内为每个候选分配 facts sequence、构造 `expire` Envelope 并写入 unified observation outbox；任一 space resolver、身份、Envelope 或 outbox 错误都会回滚整批 lease 状态、sequence 和 facts。该 seam 要求调用方提供 source 与 `scope/IP -> space_id` resolver，未接入默认 `Manager.ExpireLeases`、`sweepExpiredLeases` 或默认进程；因此批量 EXPIRE 仍不是生产统一事实链。

**Opt-in seam 增量（2026-09-14）**：新增 `lease.FactsMutationWriter`，提供 `ActivateLease/ReleaseLease` 及不提交事务的 `ActivateLeaseTx/ReleaseLeaseTx`。每次 opt-in mutation 在同一 SQL transaction 内完成 Before 快照、authoritative lease update、`facts.SequenceAllocator.NextTx`、`MutationCommand.FactEnvelope` 和 `ObservationOutbox.EnqueueTx`；提交后才调用兼容审计 observer，失败回滚 lease、allocator row 和 outbox event。补充 offered/active 状态守卫、完整 After 快照、generation 断言、caller rollback 与 invalid-state 无副作用测试。新增可选 `DNSMutationSink`，允许兼容 DNS outbox 使用同一事务写入；DNS 写失败或调用方 rollback 时，lease、facts sequence、facts outbox 和 DNS outbox 均无部分提交。随后补齐 opt-in `RenewLease/RenewLeaseTx`，覆盖 active→active、generation 严格递增和统一事实写入；并补齐单租约 `ExpireLease/ExpireLeaseTx`，明确批量 `ExpireLeases` 仍未迁移；随后补齐已有租约的 `DeclineLease/DeclineLeaseTx`，保留无租约 DECLINE tombstone 的旧路径。当前 opt-in seam 已覆盖 Activate/Renew/Release/Decline/Expire 五类已有租约 mutation；仍未覆盖 OFFER 写入、无租约 DECLINE tombstone、批量 EXPIRE、默认 DHCP handler、管理 API 和默认进程装配。已补充 `NewMutationFactIdentity`：以 source、space ID、mutation kind、lease ID、generation 生成 SHA-256 派生的稳定 EventID，同一重试可复用，跨 mutation/generation 自动区分；空身份、未知 mutation 和负 generation fail-closed。`FactsMutationWriter` 在 opt-in 调用省略 event ID 时，会基于 After 快照自动派生该稳定 ID；source 和 space ID 仍必须由调用方显式提供。该辅助仍只服务 opt-in seam，不直接切默认路径。下一步应先做真实调用方接入评审，不直接切默认路径。该 seam 未接入 `HandleRequest`/`HandleRelease`、默认构造或生产进程，N5/N6 仍为 `experimental/incomplete`。

本轮已补齐 readiness 观测收口：`Server.StartupStatus()` 接入 DHCP plane 的认证详情和 data-plane metrics，发布 `configured/ready/state/last_seq` 四类低基数状态；恢复错误原文不进入 API 或 metrics。该观测不改变默认构造，不代表 WAL durable ACK 或内存 LeaseStore 已成为生产事实源。

**DNS 迁移边界守卫（2026-09-14）**：新增 `cmd/goddi/wal_lifecycle_boundary_test.go` 的源码级守卫，确认默认进程仍通过 `dhcpinternal.NewDNSConsumer(dnsStore.DB, link)` 使用 legacy `dhcp_dns_events`；同时禁止默认进程偷偷装配统一 facts DNS consumer、`ObservationOutbox`、facts sequence allocator 或 watermark。该测试只证明迁移边界未被误接入，不证明 legacy DNS consumer 已迁移，也不改变 N6 的 `experimental/incomplete` 分类。

**P4 默认进程灰度守卫（2026-09-15）**：扩展默认进程源码级边界测试，明确禁止 `cmd/goddi` 装配或启动 `ipam.FactsPipeline`，包括启用配置、`Start/Wake/Stop` 生命周期调用及 pipeline 生命周期接口；同时继续要求默认进程保留 legacy IPAM linkage、lease observer 和 reconcile 路径。该守卫只证明灰度组件没有误接入默认生产路径，不证明统一事实链已生产化。

**P4 producer 恢复前置闸门（2026-09-16）**：`FactsPipelineOptions` 新增可选 `BeforeStart` 回调。启用灰度 pipeline 时，必须先通过调用方提供的 producer/WAL 恢复检查，成功后才启动 FactsConsumer；回调失败时保持 consumer `idle/unstarted` 并原样 fail-closed 返回，避免 control-side projection 在 producer baseline 未就绪时先运行。禁用模式不执行该回调，仍保持 legacy 回滚 no-op。该机制仅提供显式启动顺序契约，未接入默认 DHCP、默认 WAL 或默认进程。

**P4 producer 提交后唤醒（2026-09-16）**：`FactsMutationWriter` 新增可选 `WithPostCommitWake` 回调，仅在 opt-in mutation transaction 成功 commit 后调用；事务开始失败、事实写入失败或 rollback 均不会唤醒 consumer。该回调可连接 `FactsPipeline.Wake()`，形成“producer commit → wake → consumer replay”顺序，但不会把事务句柄泄漏给异步消费者；新增成功提交/失败回滚唤醒次数测试。默认 DHCP mutation 调用点仍未接入。

**P4 生命周期上下文边界（2026-09-16）**：`FactsPipeline.Start/Stop` 在启用模式下先拒绝 nil context，再执行 `BeforeStart` 或 consumer 生命周期，避免恢复回调和异步 runner 收到不可取消的空上下文；禁用模式仍保持 no-op。新增测试确认 nil context 不会触发 producer recovery callback，pipeline 保持 idle/unstarted。

**P4 启停幂等边界（2026-09-16）**：`FactsPipeline` wrapper 增加串行启停保护：重复 `Start` 在 consumer 已启动后 fail-closed，避免创建第二个 replay runner；`Stop` 在未启动或已停止时安全返回，正常停止后状态保持 `stopped`。新增 wrapper 层重复 Start/Stop 测试；consumer 实例仍遵循“一次生命周期、停止后不得复用，需重新构造”的原有约束。

**P4 并发启停边界（2026-09-16）**：新增并发负向测试，8 个并发 `Start` 仅允许一个 runner 成功，其余调用 fail-closed；8 个并发 `Stop` 均安全返回，最终 consumer 保持 stopped 且不运行。该测试仅验证 opt-in wrapper 的生命周期串行化，不扩大默认生产装配范围。

**P4 失败启动重试边界（2026-09-16）**：固定 `BeforeStart` producer/WAL 恢复闸门失败后的重试语义：首次回调失败时 pipeline 保持 `idle/unstarted`，不设置 wrapper 的 started 标记；恢复条件修复后再次 `Start` 会重新执行闸门并允许启动唯一 FactsConsumer runner。新增测试确认失败尝试不会锁死 pipeline、回调次数准确、成功重试后可正常 Stop；默认路径和灰度装配边界不变。

**Replace/SetPools/Upsert/Remove/Claim/Query fail-closed 收敛（2026-09-14）**：兼容性的 `MemoryIndex.Replace` 现在复用 `ReplaceChecked` 的完整快照校验；新增 `SetPoolsChecked`、`UpsertChecked` 与 `RemoveChecked`，并让兼容性的 `SetPools`/`Upsert`/`Remove` 复用统一校验。`ClaimAvailable` 增加 nil receiver、空 scope ID、空 lease ID 和负 generation 校验；`Get`、`ByMAC`、`HeldByIP` 和 `FindAvailableIP` 对 nil receiver 或空查询键 fail-closed。统一校验 lease status 和 generation，未知状态或负 generation 不得进入索引。输入非法或包含重复 lease ID/重复 scope pool 时直接拒绝发布，旧索引和旧 pool 快照保持不变；合法但不存在的删除保持幂等。需要获取错误的恢复/启动路径继续使用 Checked API；该修改消除了兼容 void API 静默发布无效快照、错误写入、误删或无效查询的风险，同时不改变默认 DHCP 仍使用 SQLite 的边界。

**facts 观测补充（2026-09-14）**：`ObservationOutbox.Status()` 现在返回 pending/failed、durable head sequence 和首个 outstanding sequence；`FactsConsumerStatus` 同时报告 applied watermark、next expected sequence、head、first outstanding、lag 和 gap，并以 `Readiness()` 提供保守的 opt-in readiness 分级。另增 `internal/metrics` 的 opt-in provider 与低基数 Prometheus gauges：`goddi_facts_consumer_pending`、`failed`、`applied_sequence`、`lag`、`gap`、`readiness`。空 domain 被丢弃，状态和错误原文不进入 label；该 provider 未由默认进程注册，未接入默认 `/ready`，因此只证明观测契约存在，不证明统一事实链已生产化。
8. 继续保持默认 `dhcpserver.New` 为 SQLite，直到本批所有退出条件满足。

**旁路审计补充（2026-09-13）**：管理 API 的 `DeleteDHCPLease` 在 authoritative 主模式下直接调用 `LeaseMgr.ReleaseLease`，副本模式有拒绝写保护；metrics 的 `ScopeUtilization` 为 authoritative store 只读采样，不是写旁路；backup 的 `VACUUM INTO` 与停服 restore 属于离线复制/恢复，不是运行时 mutation，但不应被计入 WAL replay 证据；`sweepExpiredLeases` 仍通过 `ExpireLeases` 批量裸 SQL 更新后再分别执行 HA、DNS outbox、IPAM observer，尚未纳入 `MutationContract` 或 WAL。上述路径继续标记为生产迁移前置缺口。

**EXPIRE DNS 语义收敛（2026-09-15）**：审计确认 `sweepExpiredLeases` 不重新检查 `DNSUpdates` 有明确实现依据：该开关控制未来 DHCP DNS create/re-publish，过期清理用于撤销历史 DHCP-owned record，删除操作幂等且不会重新发布记录；若关闭开关后跳过删除，可能残留历史 ownership。新增 `TestLinkage_ExpiredLeaseWithdrawsHistoricalNameWhenDnsUpdatesDisabled`，覆盖“先发布记录、再关闭 `dns_updates`、租约过期、仍排队 delete、记录最终撤销且 lease 变为 expired”，并钉住不产生 create。该策略与 `RELEASE/DECLINE` 的实时路径差异已明确记录；未改变默认 DHCP 热路径或统一 facts 接入边界。

**关闭与恢复审计补充（2026-09-13）**：`Server.Shutdown` 现在对关闭操作使用 `sync.Once`，先停止 admission、关闭监听器，再等待 receive loop 和 request worker；worker 未完成时，调用方的 context 取消返回其错误，固定 5 秒上限返回 `ErrShutdownTimeout`，不再把未完成 drain 报告为成功。关闭不会删除 WAL，已 durable 但尚未投影的事件仍由 staged applier 的启动 replay 接管；`Server` 仍不拥有 `AsyncApplier`，因此全局 WAL/applier drain 顺序必须由外层装配方显式负责。该改动仅收紧 fail-closed 语义，不改变默认 SQLite 构造、默认 ACK 路径或 WAL durable ACK 接管状态。

**AsyncApplier 关闭契约补充（2026-09-15）**：新增显式 opt-in `DrainAndClose(ctx)`：先等待调用前已接受的队列和 in-flight apply 完成，再执行关闭；超时或取消只返回上下文错误，不将 applier 假报为已关闭，后续仍允许由外层装配方继续处理或交给 WAL 启动 replay。原 `Close()` 保持 abortive close 语义，仍停止 admission 并保留未投影 durable event 供恢复重放。该 API 仅收紧迁移期装配契约，未接入默认 DHCP 或全局进程。

**P1 外层 WAL 生命周期契约补充（2026-09-15）**：新增显式 opt-in `lease.WALLifecycle`，将 producer admission 与关闭边界分离于 DHCP `Server`：正常写入执行“WAL append → WAL Sync → AsyncApplier Submit”；关闭先固定 admission cutoff，再按“WAL Sync → `AsyncApplier.DrainAndClose(ctx)` → WAL Sync → WAL Close”顺序执行。排空超时/取消只返回上下文错误，WAL/applier 保持可由外层处理的状态，已 durable 未投影事件仍可在下一次 `OpenWAL`/`Replay` 中重放；关闭期间新写入 fail-closed。新增成功排空、并发关闭、超时后 durable replay 和 nil 依赖测试；P1 仍为 opt-in，默认 DHCP SQLite、默认进程和 durable ACK 接管边界未改变。

**P4 统一事实链灰度装配评审补充（2026-09-15）**：新增显式 opt-in `ipam.FactsPipeline` 作为 control-side 灰度装配边界。默认 `FactsPipelineOptions.Enabled=false` 时不创建、不启动、不访问 FactsConsumer 依赖，`Start/Wake/Stop` 均为安全 no-op，状态保持 `Enabled=false/idle`，用于回滚至 legacy DHCP-DNS-IPAM 路径；只有显式启用时才构造同库 `FactsConsumer`，并按“producer 启动/恢复完成 → pipeline.Start → producer 提交事实后 pipeline.Wake → pipeline.Stop”顺序运行。构造期继续拒绝 producer/control 分离数据库；consumer 未启动、lag/backlog、gap、failed 事件分别保持 `unconfigured`、`degraded` 或 `failing`，Stop 超时不假报排空成功。新增禁用 no-op、启用启动/停止、分离存储拒绝测试；未接入默认 DHCP、默认 DNS 或默认进程，P4 完成后 N6 仍为 `experimental/incomplete`。

## 四、依赖关系与建议顺序

```text
N5 生产 LeaseStore 前置收敛
 ├── N6 统一 DHCP-DNS-IPAM 事实链
 └── N7 多节点配置协调评审
       └── N8 外部验收执行
```

建议顺序：

1. **先执行 N5**：生产 LeaseStore 是 N6 和真实 HA 的基础，但 N5 只完成契约和装配评审，不直接切默认路径。
2. **随后执行 N6**：统一事实链必须明确 DHCP mutation 与 DNS/IPAM projection 的恢复边界。
3. **并行准备 N7**：先把多节点协议、持久化和 fencing 设计审清，再决定是否实现 transport。
4. **环境具备后执行 N8**：真实验收独立于仓内原型，不能用 N5/N6/N7 的模型测试代替。

## 七、本轮不实施的内容

在用户确认前，本轮不执行：

- 默认 DHCP Store 切换；
- `ClaimAvailable` 接入 `LeaseStore` 或 `HandleDiscover`；
- `ClaimAvailable` 的 generation 已收敛为迁移期契约：仅接受 generation=0 的新 offered lease；REQUEST/Activate 才推进到 generation=1，后续 Renew 按 MutationContract 递增；GenerationIncrement 在达到 int64 最大值时 fail-closed，避免 SQLite/WAL/facts generation 回绕；该校验仍只作用于 opt-in MemoryIndex，不代表默认 DHCP 已迁移；
- WAL durable ACK 默认启用；
- 删除或弱化 cluster 501；
- 把统一事实链、多节点 HA、真实掉电/relay/分区/容量/长稳标记为完成；
- 提交、推送或发布新版本。
