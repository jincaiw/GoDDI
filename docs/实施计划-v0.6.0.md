## 零、本计划的三项强制修正

v1.0 方案中有三处建议已被 v1.1 再评估**撤回**，本计划不执行 v1.0 的原始表述：

| 编号 | v1.0 原始表述 | 本计划的执行口径 | 依据 |
|---|---|---|---|
| X1 | T2「落库改为**异步 WAL 队列**」，先 ACK 后落库 | **反转**：租约必须与 outbox **同事务可靠持久化后才 ACK**；异步只用于 DNS/统计投影，绝不用于租约事实本身 | RFC 2131 §3.1 第 4 步；当前 REQUEST 已是先写库再 ACK，不得倒退 |
| X2 | §5.5「DHCP 用 **split-scope 80/20** 为主方案」，即视为完整 HA | **降级**：拆池只是**地址空间划分**，不保证原 IP 续租、备用容量有限，不得对外称故障接管；HA 走单写热备 + 持久确认 + 围栏接管 | Microsoft split-scope 设计说明；v1.1 §6.2 |
| X3 | 「数据面自治 → 控制面短时不可用**不影响业务**」推论出进程内隔离足够 | **收紧**：同进程无法隔离 `os.Exit`、致命 OOM、整进程重启；需同程序包提供 `control / dns / dhcp` 三个角色由系统分别托管 | v1.1 §5.1、E01 |

另有两处表述需要限定：
- v1.0 的成熟度评分（C+）**不构成生产认证**，不得作为上线依据。
- v1.0 的验收基线「DNS ≥ 60,000 QPS」等来自历史测试（标记 H），本轮未复现硬件，不能作为容量承诺。

## 三、批次明细

### B0 — 故障契约 + DNS 协议止血

#### B0.1 W02 故障契约 ADR（**已接受**）

产出：`docs/adr/0001-fault-contract-and-state-ownership.md`（状态：已接受，2026-09-10）

必须冻结的不变量（已冻结）：

1. **状态所有者唯一**：租约事实由 DHCP 引擎写；地址授权由 IPAM 写；RRset 由 DNS 写。任何跨域写入必须经对方接口，不得直写对方表。
2. **ACK 前置条件**：只有在租约与变更事件**同事务持久化成功**后才可发送 ACK。持久化失败即不 ACK。
3. **控制面与数据面故障隔离**：管理进程退出/重启不得中断 DNS 解析与 DHCP 续租；租约引擎不依赖控制库在线。
4. **围栏先于接管**：未确认隔离旧主时，备节点**不得**接管写；不得仅凭心跳 promote。
5. **恢复以 ACK 集合为准**：故障恢复后以「客户端已收到 ACK 的集合」核对，不以内存或日志条数核对。
6. **降级必须显式**：双节点故障后只能在「严格双副本暂停」与「用户批准的单副本降级」之间二选一，不得静默降级。

标注：2、3、4 的**具体实现形态**已由第六节的设计输入确定（仅 IPv4 / 严格双副本 / 三角色托管 / WAL+FULL / 企业 CA+ACME）。

### B4 — 数据面隔离与租约独立库（W07）

- 同一二进制提供 `control / dns / dhcp` 三个角色；all-in-one 保留为体验模式但**不宣称同等隔离**。
- DHCP 本地 `leases.db` 独立于控制库；租约与 outbox 同事务。
- 数据面冷启动：控制面不可用也能从本地快照启动。
- 资源额度与故障探针；管理进程 kill 不影响数据面。

验收：`kill` 管理进程后 DNS 解析与 DHCP 续租不中断；租约库写失败时**不发送 ACK**。

进度：第二条验收条件（写失败不发 ACK）**已满足并有回退用例**（W07-b1）。第一条「`kill` 管理进程后 DNS 解析与 DHCP 续租不中断」在 **W07-b2** 之后成立：DHCP 侧在 b1 完成，DNS 侧在 b2 完成（zone store、AXFR/IXFR、动态更新全部改为读写本地副本，`dhcp_dns_events` 的出站队列由 DNS 面自己消费）。**仍不成立的是「管理进程 kill 后 DHCP 动态记录的发布不中断」**：消费者已经在 DNS 面，所以不再依赖管理进程活着，但 DHCP 面欠下的事件要先上行到控制库、再下行到 DNS 面——控制库不可用期间产生的事件要等它恢复后才追得上。这是本轮如实标注的边界，不是遗漏。

**W07-d 之后**，这条边界有了一个可被机器读到的表示：控制库不可达时进程报 `degraded`（而**不是** 503），运维与编排层都能看见「还在服务，但有一件事要处理」。把降级报成不健康，会让编排层重启那个唯一还在正常服务的进程——那是本条验收条件想避免的事故本身。

**W07-d 完成记录（2026-09-10）**

这一轮把「这个进程现在到底行不行」从一句启动日志变成一个有级别的、可被机器读的答案，并给数据面的本地占用装上了只报警不拦人的上界。

实施前确认了四个分叉（均由助手评估后选定）：探针语义分离、数据面-only 角色不加探针端点、额度只管租约数与文件大小且越界只降级、`/ready` 粗粒度未认证。

**先修一个反向的行为。** `/health` 原来在子系统降级时返回 **503**。对 liveness 探针而言这是反的：编排层会重启一个被判定为不健康的容器，于是它重启的正是那个「控制面已经不在、但仍在用本地副本正常服务」的进程——整个 B4 想消除的故障。现在 `/health` 只回答「进程在跑」，降级由 `/ready` 报告。

**三级，不是两级。** `degraded` 是「还在干活，但有话要说」——控制库不可达（本地副本仍在服务）、额度越界、某条上行队列没在排空。它**仍然返回 200**：把正在正常服务的实例移出服务，等于把它警告的那个caveat 变成真正的故障。只有 `failing`（副本状态读不出来、监听器没起来）才是 503。告警读 body，负载均衡读状态码。

**未认证的探针不碰库。** `/ready` 必然未认证——需要凭据的探针是编排层用不了的探针——所以它只回级别，且**只读内存**（`Runner.Probe()` 返回上一趟 pass 存下的视图）。理由与 `/metrics` 需要认证同源：一个未认证、又要拿 store 那唯一一条连接的端点，是让任何人掐死它正在上报的那条请求路径的方式。数字与原因走已认证的 `/api/v1/system/dataplane` 与 Prometheus。

**额度是信号，不是闸门。** DHCP 服务器因超出配额而拒发地址，比超配额本身糟得多，而且它恰好在人已经被叫醒的时候发生。所以越界只置 `degraded` 并写一行日志。三个上界：租约数（ADR 0001 的两万口径）、store 文件字节（含 `-wal`；WAL 模式下主文件可能落后日志一个 checkpoint，只量主文件正好漏掉这个上界要抓的增长）、单条上行队列积压。`0` 用默认，**负值表示关掉**——两种写法是不同的意图，合并会让「没写」静默变成「关掉」。

**新探针第一次跑冒烟就抓到了一件旧检查漏掉的事。** `scripts/w07_role_smoke_check.py` 一直只断言启动日志，而 `role=all` 的进程里 DHCP 监听器**从来没起来过**（非 root 绑不了 `udp4 0.0.0.0:67`），日志里那行 `failed to start DHCP server` 没有任何断言看着它。新探针把它变成 `failing`，`/ready` 立刻报 503——这是探针在正常工作，不是回归。于是冒烟脚本改成**两源一致性断言**：`/ready` 的答案必须与进程自己的启动日志一致（监听器全都起来 → ok/degraded；有没起来的 → failing 且 503）。这比「必须 200」强：它同时钉住了两个方向，而且不会因为跑测试的用户没有特权而变成噪音。

**检查器自身误报过的两次（记在 ADR 0002 里，不只留在 commit 里）**：

1. **按换行切语句** → 多行 `CREATE TABLE (…)` 被切成碎片，列定义被报成「不认识的语句」。SQL 语句的边界是分号，不是换行。

**W12-b 未验证项（如实标注）**

1. **没有真正的「更新的二进制」**：闸门是靠「manifest 说谎的归档」驱动的。走的是同一条代码路径、同一形状的输入，但**不是**第二个 build。构造第二个 build 需要额外的构建产物与版本号，本包未做。
2. **`--into` 在闸门判定前就已经解包**：`ReadSnapshot` 单趟完成「校验 + 解包」，所以被拒绝的 `--into` 仍会在指定目录留下文件（`--in-place` 走临时目录、随 `defer` 消失，不受影响）。拒绝信息里明说了这一点，但**没有阻止**。要阻止就得先 `InspectSnapshot` 再 `ReadSnapshot`，对多 GB 归档是两趟 I/O——这个取舍未经测量。
3. **`--status` 打开已有库时是读写打开**（不施加 PRAGMA）：在 WAL 库上这可能创建 `-shm`，未观测也未断言。

6. **检查器不解析的语法一律拒绝**：块注释（`/* */`）与跨行字符串会被拒绝并要求改写，而不是猜着解析。这会拦住一类合规的迁移，是刻意的取舍。
7. **R4 不量化回填规模、R5 不机器检查**：从大表批量复制的 `INSERT … SELECT` 或全表 `UPDATE` 的**耗时**没有判据，而它跑在服务启动期；当前最大表规模（≤2 万租约）下可接受，规模上一到两个数量级后需重审。

**进程级断言（`b5_surface_smoke_check.py`）**：

1. **未配置白名单时管理面照常开放**——空的 `admin_allow_cidrs` 是 no-op：`POST /api/v1/auth/login` 不是 403；`GET /metrics` 无令牌是 **401**（路由存在且受鉴权，不是 404）。
2. **白名单指向外部网段时**（`10.99.0.0/16`，不含 127.0.0.1）——管理面 403 且**拒绝信息说明原因**；而 `/health` **仍 200**、`/ready` **仍可用**。探针注册在白名单**之上**是刻意的：编排器探针被拒会重启一个正在正常服务的进程。
3. **白名单是 `/metrics` 上的外层中间件**——名单外来源得到 **403 而不是 401**，即「先按地址拒，再谈令牌」；否则一个无论如何都会被拒的来源，能从 401→403 的差别里得知自己递的令牌是否有效。
4. **读不出的白名单条目让进程拒绝启动**并**点名 `admin_allow_cidrs`**，端口上没有任何东西在监听。这就是 fail-closed 真正被走到的形态——中间件自己的兜底在校验过的配置下永远到不了。

**本包抓到的两个真问题（都不是被测代码的缺陷，而是「验证」本身的缺陷）**：

1. **回退脚本被中断会留下脏树**。一次运行在用例中途被杀，`finally` 里的还原没执行，`internal/dhcp/lease/audit.go` 留在变异态。后果不是「这条用例失败」，而是**下一轮**读到一个已不匹配的文件 → 报 `SKIPPED-NOT-FOUND`，同时让一个与该用例**无关**的包变红。已修两处：① 每用例**开跑前**先检查「变异是否已在文件里」，是则报 `DIRTY-TREE` 并失败，不做任何编辑；② 全部还原后，除「各 touched 包重新变绿」外，再逐文件断言**原文已回来**（`TREE-CLEAN`）——包变绿与文件还原是两件事。
2. **loopback 请求走了本地代理**。这台机器导出 `http_proxy=http://127.0.0.1:1082`，而 Python **不**为 `127.0.0.1` 绕过代理。于是「进程已退出、端口不该有人应答」这条断言测到的是**代理自己的 503**。已修：所有请求走 `ProxyHandler({})` 的 opener；「有没有人在监听」改用**裸 TCP 连接**判断，与代理彻底无关。

## 八、D1 决策记录：拆分后的 DDNS 生效时间（2026-09-10，**已实施**）

### 问题

记录的作者是 DNS 面（W07-b 第二次切分的确认结果）。一条绑定确认后，事件要经过 **DHCP 本地 outbox → 上行推送 → 控制库 → 下行同步 → DNS 面副本 → 消费者排水** 才变成可解析的名字。两段轮询原本默认各 5s、消费者排水 1s，因此**上界约 11s**，而 Phase 0 退出条件写的是「DDNS 生效 ≤ 2s」。两者必须对齐一个。

### 决定：**近端事件唤醒 + 轮询默认 1s**（不改退出条件，不做同进程快路径）

三个延迟项逐项处理，能压到接近零的压到零，剩下的才是轮询：

| 延迟项 | 处理 | 依据 |
|---|---|---|
| ①DHCP 面「欠一条记录」→ 控制库 | **入队后立即唤醒本面上行推送**（`Runner.Wake`，由 `Server.SetOutboxWake` 在 `enqueueDNSEvent` 成功后触发），不再等轮询 | 这一步是**本进程自己产生**的变更，落在自己的库、由自己的循环推送，没有理由等定时器 |
| ②控制库 → DNS 面副本 | 轮询默认 **5s → 1s** | 这一步只能靠拉取：消费者是另一个进程、另一个文件系统，没有任何通道可以通知它 |
| ③副本 → 记录可解析 | 消费者 1s 排水（不变，也不可配） | 现在的实现 |

**为什么不做同进程快路径**（曾经列出的候选 ③）：让 DNS 面在 all-in-one 时直接读租约库的 outbox，会把「消费者状态写回 DHCP 面的文件」这件事重新引进来——那正是 W07-b2 划走的边界（outbox 的 `status`/`attempts` 属于**每个消费者自己**）。而且它只对单进程有效，拆分部署仍要两段轮询，等于多维护一条生产上不常走的路径。

**为什么不改退出条件**：2s 是「客户端刚拿到地址，立刻解析自己的名字」这条体验的合理上界；把它改成 11s 等于承认拆分让 DDNS 变得不可用，而那不是必要的代价。

### 代价（已实测，不是估计）

- **轮询次数 ×5**。一个空闲 pass 的成本在 **2 万租约**（ADR 0001 的容量口径）下测得 **123µs**（`TestTheCostOfAnIdlePassAtTheDocumentedLeaseCeiling`），即 1s 间隔下约占 0.012% 的时间。原因是 pass 由**标记表**驱动（`pendingRows` 以标记表为驱动表 LEFT JOIN 源表），空闲时标记表为空，不随租约总量增长。
- **同一改动顺带把另外两处延迟从 5s 降到 1s**：控制台 DHCP 事件日志的可见延迟、以及 all-in-one 里控制台记录编辑的生效延迟（后者 v0.5.2 是立即生效，现在 ≤1s）。

### 配套改动

- `internal/dataplane/runner.go`：`wake`（容量 1 的缓冲）+ `Wake()`（非阻塞发送，请求路径可安全调用）+ `Run` 的 `select` 增一路；`RunnerConfig.Interval` 的注释改正——它现在**确实**界定了「客户端等多久」，不再只是「配置漂移多快」。
- `internal/dhcp/server/server.go`：`outboxWake` 字段 + `SetOutboxWake`，在 `enqueueDNSEvent` 成功后触发；**改写**原来那段「没有唤醒可发」的注释——它把「消费者无法被唤醒」（对）与「本面的推送无法被唤醒」（错）混成了一句。
- `internal/config/role.go` + `config.yaml`：默认 `sync_interval_seconds` 5 → 1，注释写明它是客户端路径上的延迟项。
- 用例：`internal/dataplane/runner_test.go`（唤醒生效、信号不丢、不阻塞请求路径、空闲 pass 成本）、`internal/dhcp/server/outbox_wake_test.go`（入队才唤醒；未装配时照常服务）、`internal/config/role_test.go`（默认值满足 2s 界 + **随包发布的 `config.yaml` 必须与常量一致**——只改常量不改文件是这次差点踩到的坑：装出来的实例仍然读文件里的旧值）。
- 回退验证：`scripts/w07_revert_check.py` 增至 **33 项**，新增 R32（关掉 `wakeOutbox`）、R33（`Wake` 不发信号）、R34（缓冲改无缓冲）、R35（默认值回到 5s）。33 项全部如预期失败，五个包（新增 `internal/config`）恢复后全绿。

### 遗留（如实标注）

1. ~~**端到端未计时**：2s 是三项上界之和，没有一条用例从 ACK 量到解析成功。~~ → **已计时（收口记录见第九节）**：`internal/dhcp/server/ddns_latency_test.go` 从真实 UDP 上的 ACK 量到真实 UDP 上的 DNS 应答，一轮预热加三轮实测，最慢 **2.0011s**（1.9995 / 1.9950 / 2.0011，彼此相差 6ms）。撤销 `SetOutboxWake` 后同一用例测得 **3.001s** 并失败，所以这个数字确实在量唤醒，不是两段轮询的复述。**判据是 2.25s**（2s 界 + 0.25s 调度余量，理由见第九节 F.1）。

   **实测的结论是：界成立，但余量为零。** 2s 不是「三项上界之和」这种悲观估计——它就是这套实现的**常规**值。两段 1s ticker 在同一进程里相隔微秒启动，相位恒定，消费者的 tick 总是落在「同步刚写完那一行、本轮已经错过」的缝里，于是每一轮都付满 1s + 1s，剩下的时间连两项之间的处理都装不下（实测超界 2.7ms，靠断言的 100ms 调度余量才不至于偶尔翻红）。这不是可以靠机器更快的量：界本身等于 2×轮询周期。
   **建议的下一步（本轮未做，因为它是一次产品改动而不是一次测量）**：让下行同步在把 DDNS 事件搬进来之后唤醒消费者（`DNSConsumer` 现在只有 1s ticker，没有 `Wake` 的对应物），或把两条轮询周期错开/减半。任一条都能把常态值从 2.0s 拉到约 1.0s，重新拿到余量。**在那之前，2s 是一个「成立但脆弱」的承诺**：任何让这两段轮询更慢的改动都会立刻把它顶破，而 `latencySlack` 之外的余量并不存在。
2. **消费者的 1s 排水不可配**，也没有回退用例能通过移除它来失败（脚本「刻意不声称」清单已记录）。第九节的用例**不是**这条的回退用例：它撤掉的是唤醒，测到的是 3s 而不是「移除排水后失败」。
3. **未在 2 万租约 + 真实客户端的压力下验证** 1s 轮询与控制库写入的相互影响。

**修掉的缺陷（迁移 020，未发布）**：回填写成 `SET space_id = (SELECT s.space_id FROM ipam_subnets s WHERE s.id = ipam_history.subnet_id)`。标量子查询在无匹配行时产出 **NULL**，撞上 `ipam_history.space_id` 的 `NOT NULL`，于是 `NOT NULL constraint failed: ipam_history.space_id` **让整个数据库升级失败**——不是丢几行，是这台节点起不来。孤儿历史行可达：`sqlite3` CLI 默认 `PRAGMA foreign_keys = OFF`，而本计划的运维流程里明确有直连库的操作；应用自身在 `subnet.go` 里显式删除历史行，正说明它不依赖级联（「一条不被强制的约束不是保证」）。现在用 `COALESCE(..., '')`：孤儿行得到空串，而不是 NULL。**空串是诚实结果**——凭空借一个 space 会把别人的变更记进本 space 的历史。

顺带修的：唯一索引失败时的排查查询原来 `GROUP BY space_id, ip_address` 却**没 SELECT `space_id`**，而修复是按 space 做的；没有那一列，运维只知道「撞了」而不知道去哪个 space 找。同时把原因从「`checkOverlap` 被绕过」扩成「被绕过**或**某个子网事后被扩大，以致覆盖了另一个子网的地址」。

**变异校验**：去掉 `COALESCE` → 精确复现 `NOT NULL constraint failed`，用例 `--- FAIL`；文件逐字节还原。`ipam` / `address` / `space` / `subnet` / `database` 五包全绿。

### C. DDNS 端到端延迟：第一次有数字

新增 `internal/dhcp/server/ddns_latency_test.go`：四库联动（控制库 + 租约库 + DNS 副本库 + 控制模式），真实 UDP 收 REQUEST、真实 UDP 查 DNS，全链路都是产品自己的代码——真实的 receive loop、真实的 lease manager、真实的 outbox、真实的带上行推送与唤醒、真实的向下同步、真实的消费者、真实的 zone store。

一轮**不计时**的预热（第 0 轮）加三轮实测（数字为最终设计，2026-09-12 重打后复测）：

| 轮次 | 名字 | 地址 | ACK → 可解析 |
|---|---|---|---|
| 0（预热，不计入） | `lat0.e2e.latency.test` | 192.0.2.100 | 2.005s |
| 1 | `lat1.e2e.latency.test` | 192.0.2.101 | **1.9995s** |
| 2 | `lat2.e2e.latency.test` | 192.0.2.102 | **1.9950s** |
| 3 | `lat3.e2e.latency.test` | 192.0.2.103 | **2.0011s** |

三轮彼此相差 6ms，**结论：2s 界成立，但余量为零**，原因不是抖动而是相位锁定（见第八节遗留 1）。判据是「最慢一轮超过 2.25s 才算多等了一轮」——多出的 0.25s 是给 CI 调度的，不是给设计的。**撤销 `SetOutboxWake` 后同一用例测得 3.001s 并失败**，所以这个数字确实在量唤醒，不是两段轮询的复述。复现脚本：`scripts/d1_ddns_latency_check.py`（跑测量 + 做那处变异 + 逐字节核对还原）。

**预热那一轮不是装饰**：它在 CI 上量到 2.130s（后两轮 1.862s / 1.994s），差额全在冷启动里，曾经把用例判红——见第九节 F.1。同一节还记了另一件事：这个数字是**相位量化**的（≈2s 或 ≈3s 一档），所以单次运行的变异门禁可能落在快档，脚本因此重试一次。

**这个测试刻意不声称的**（同写在文件头部，因为「四库联动」很容易被读成「等于生产」）：DHCP socket 是环回上的临时端口而不是 :67（绑 :67 需要权限，且本机被容器运行时占着），因此没有广播、没有 relay、被服务的「接口」是一个钉住了地址的名字而不是真实网卡；应答的目的地址是广播地址，环回上并不存在，所以 socket 被包了一层把广播改投给唯一那个客户端——这层替身替代的是链路层，报文本身仍是 `sendResponse` 自己产生的；解析器是 `miekg/dns` 直接架在产品 zone store 上，完整的 `internal/dns/server` 走真实 UDP 由 `scripts/w14h_split_outage_drill.py` 覆盖；单机，所以没有平面间的网络往返与时钟偏差。

**E.2 浏览器回归 9 条：两族 spec 对环境的要求互斥**

失败全在两个**本批新增**的 spec（`config-versions` 2 条、`ipam-console` 7 条），**不是产品缺陷**，是它们各自需要一种 CI 从来没提供过的环境：

* `config-versions.spec.ts` 原先取「最新的 `dns_zone` 修订」当工作对象。**修订比资源活得久**（历史刻意不随删表级联），而空库上最新的那条 `dns_zone` 修订属于 `api.spec.ts` 末尾**自己删掉**的那个 zone → `POST /config/publish` 返回 404 `configver: resource not found`——这是**正确**行为。本地之所以一直绿，是因为 `scripts/w13_frontend_smoke.py` 会 seed 一个活跃 zone，恰好把它掩盖了。

1. `config-versions.spec.ts` 改为**每个用例自己建 zone**（新增 `createZone()`），并给行定位加上 `resource_id` 收窄——每个资源的历史都从修订 1 开始，`dns_zone` 与 `dns_records` 又共用 resource id，「第一个 #1」不是它的。于是它不再依赖任何环境。

**E.3 这条的教训**

「未被验证的机制如实标注」这次又是应验在**验证环境**上：这两个 spec 只在本机（有 seed）验过，判据写的是「本机通过」，于是 CI 第一次跑就暴露出环境依赖。同理，`golangci-lint` 从没在本地跑过，4 条告警里有一条是生产代码的死方法——**本地门禁的清单本身就是一条要维护的断言**。

### F. 重打之后：两条绝对墙钟阈值（2026-09-12）

重打后的 CI：`lint` ✅、`vulncheck` ✅，但 `test` 与 `Release` 各挂一条，**两条都是墙钟阈值，不是产品缺陷**——而且两条都在**不同的二进制**上被量。

**F.1 `internal/dhcp/server` `TestTheTimeFromAckToResolvableIsWithinTheBound`（本批新增，Release 口径挂）**

实测 `round 0 = 2.130s`，而 `round 1/2 = 1.862s / 1.994s`。**差额全在第一轮的冷启动里**（客户端第一次发 UDP、zone store 第一次查询、解析器第一次分配），与设计无关，而断言取的是「最慢」。修法两步：

1. **丢掉一轮预热再测**（`latencyWarmup = 1`，`.env` 里 pool 从 3 个地址加到 4 个）——和 `internal/dataplane` 那条「One pass to settle, then measure」同一套纪律；余量从 0.1s 提到 0.25s（判据 2.25s，防止把 CI 的调度算成设计）。
2. 顺带搞清了一件此前写错的事：**这个数字是相位量化的，不是抖动的**。撤掉唤醒后实测到 `3.006 / 2.995 / 2.997 / 2.999s`（一个进程四轮全在**慢档**），但也见到过**同一份代码**报 `1.994s`（**快档**）——落在哪一档由进程启动时两个 ticker 的对齐决定，与机器忙不忙无关。所以「撤掉唤醒必须失败」这条门禁在快档下会失效：`scripts/d1_ddns_latency_check.py` 因此**重试一次**再下结论（两个独立进程的相位互不相关），并把这条局限性写进脚本文件头与 EXPECTED 注释。第八节原先记的「3.000s」是一次观测，不是定律。

**F.2 `internal/dataplane` `TestTheCostOfAnIdlePassAtTheDocumentedLeaseCeiling`（W14 既有，CI `-race` 口径挂）**

CI 报 `179ms`，界是 `100ms`。同一台开发机上这个 pass 量到：

| 二进制 | 实测 |
|---|---|
| `go test ./internal/dataplane/` | **1.1 ms** |
| `go test -race ./internal/dataplane/` | **46 ms** |
| `go test -race`（CI，4 vCPU 共享） | **179 ms** |

**40 倍**的差额来自 race 插桩本身。拿一个**插桩过的**数字去比一个**未插桩的界**，量的是插桩器而不是产品。修法：用构建标签把「哪个二进制」写进判据——`internal/dataplane/race_detector_race_test.go`（`//go:build race`）与 `race_detector_test.go`（`//go:build !race`）各定义 `raceDetectorEnabled`，`-race` 下界放宽到 500ms，普通构建仍是 100ms，并且日志里打出用的是哪个界。**紧界并没有被丢掉**：`release.yml` 每个 tag 跑的就是普通 `go test ./...`，本地默认也是它。

**F.3 教训**

**绝对墙钟阈值必须在「哪个二进制、哪台机器」上说清楚。** `-race` 与共享 runner 是两个不同的世界，而一条没有说明这些的阈值断言，红的时候分不清是产品退化和环境噪声——这次两条都属于后者，但把它们当成前者去改代码就会改错地方。

**验证**：`gofmt -l` 干净 · `go build ./...` · `go vet ./...` · `golangci-lint` **0 issues** · `go test ./...` 与 `go test -race ./...` **各 42 ok / 11 no-test-files / 0 FAIL** · `scripts/d1_ddns_latency_check.py` 实测 **2.000s**、撤掉唤醒 **3.001s 且用例失败**、还原逐字节一致且包全绿 · 浏览器两族仍 **20/20 + 8/8**。
