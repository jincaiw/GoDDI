# 关键分支覆盖 — W14-b / W14-d / W14-e

> W14-b 的枚举表与缺陷表在下面第一至三节。W14-d（耐久与崩溃一致性）与 W14-e（容量与长稳）
> 另立一册 `docs/耐久与容量-w14.md`；本文件只在 §2.2、§2.8、§四、§六、§七 里接入它们的
> 用例与数字。

> 对应实施计划 §四「关键包覆盖：dhcp / ipam / audit / database 从 0 起步到具备关键分支用例
> （**不以平均值替代**）」，以及 §B6 的「不用全仓平均覆盖率替代关键分支覆盖」。

## 一、这份文档的判据

覆盖率的分子分母是**语句**，而缺陷住在**分支**里。一个 `if` 的两条路都被执行过一次，
语句覆盖率就是 100%，尽管其中一条从没被验证过。所以本文的判据不是百分比，而是：

> 每个关键分支都有一句**能说出它做错了什么**的断言，并且这个断言**在分支被撤销时会失败**。

因此本文的主体是枚举表，每一行必须指向一个**具名用例**。撤销过的分支用变异脚本钉住
（第三、四节），没有撤销过的不冒充已验证。

覆盖率数字放在第五节，只作附录，**不作为判据**。

## 六、明确**未覆盖**的部分（诚实清单）

以下都是有名字、有原因、**没有**用例的地方。列出来是为了让「未验证」不被读成「已验证」。

| 包 / 单元 | 状态 | 为什么现在没做 |
|---|---|---|
| `internal/api/handler` 15.3%（602/3922） | **全仓最大的单块未覆盖** | 173 个 handler 是薄封装，关键判断在它们调用的 manager 里（本轮已覆盖）。真正的分支级测试需要每个路由的请求夹具；W14-c 只补了越权这一条最危险的路径 |
| `internal/dhcp/log.go` 全部 0% | 无用例 | `NewEventLogger`/`LogDHCPEvent`/`processLoop`/`flush`/`Close`/`QueryDHCPLogs`：`dhcp_logs` 上行是异步、有批、有丢弃计数的；周期刷写的分支需要有节奏的时钟，本轮没做 |
| `internal/dhcp/dns_consumer.go` 的 `Run`/`Stats` | 0% | 常驻循环与统计快照；`Drain`/`Sweep` 有用例，循环本身没有 |
