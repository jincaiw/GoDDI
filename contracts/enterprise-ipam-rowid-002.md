# Isolated IPAM reference migration 002

Migration `internal/enterprise/ipamstore/migrations/002_rowid_guards.sql` is an isolated reference-database upgrade; it is not an upstream GoDDI production migration or authorization to write. The original `001_ipam.sql` bytes and SHA-256 (`d5b68888951e6edda528cb7c19f6e7a3ae7f5b234fc12657edafb88a12688ad3`) remain frozen. The 002 SHA-256 is `9172d79d81131b13e22d36cd6c16706ecb1500d5b7e141cf16de87d3409734f3`. Version markers contain both separately.

The reviewed runner pins one physical SQLite connection, requires foreign keys, WAL and FULL synchronous mode, starts `BEGIN IMMEDIATE`, rejects attached databases and checks that TEMP schema is empty, verifies exact v1 or v2 IPAM/marker protected tables, indexes, triggers and IPAM-named views and ordered migration markers, runs integrity and foreign key checks, and rejects any rowid <= 0 in the six IPAM tables. It adds fixed BEFORE INSERT rowid-collision, AFTER INSERT positive-rowid and BEFORE UPDATE immutable-rowid guards for all six tables, then inserts the v2 marker and verifies the resulting v2 schema and data before commit. New empty references install 001 then 002 in the same transaction; reviewed isolated v1 references advance to v2. Reopening v2 repeats validation. Any failure rolls back; an unconfirmed rollback retires the connection.

For SQLite's unspecified `NEW.rowid` on implicit BEFORE INSERT, a preexisting -1 could reject legitimate automatic inserts. Positive-rowid preflight and AFTER INSERT guard prevent establishing such a state through supported reference operations. These guards may fail closed on SQLite implementations with different undefined BEFORE INSERT values; the actual pinned driver must be exercised before use. They do not protect a database against code with arbitrary schema/PRAGMA/file access or bypass of the reviewed repository. Caller must exclude concurrent use of the migration connection and stop incompatible writers throughout migration and cutover; TEMP schema is connection-local.

The runner checks protected IPAM and marker objects, not every unrelated main-schema object. Its checks are local DDL operations and do not emit a replication event. SQLite integrity and foreign key checks do not establish business invariants. The schema and rowid checks cannot prove that earlier 001 data was never replaced or lost. Historical ledger, occupancy, audit, replication continuity and ownership require independent evidence and reconciliation. A successful migration does not provide these assurances, grant a role, or establish permission for production activation.

`replicaschema` accepts and compares the exact two-version reference and markers. `dhcpholds` requires the v2 IPAM reference and no longer installs duplicate IPAM rowid guards; it still adds its own hold/occupancy coordination triggers. The documentation contract is local to this worktree; external contract publication and deployment upgrades require a separately reviewed process.
